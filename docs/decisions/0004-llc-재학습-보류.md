## 0. 전제 — 무엇이 문제인가

| 사실 | 근거 |
|---|---|
| WTW `pretrain-v0`로는 도약 불가 | 72개 명령 조합 탐색, 체공 중 수평이동 최대 8 cm |
| **WTW 공개 코드에 도약 메커니즘 자체가 없다** | `impulse_height_commands` 등 4개 설정이 어디에서도 읽히지 않는 죽은 필드. `_reward_jump`는 실제로는 몸통 높이 추종 |
| 다른 체크포인트 없음 | 로컬·상위 저장소·브랜치·릴리스·파생 저장소 전부 확인 |

⚠️ **따라서 "duty를 연다"는 표현은 정확하지 않다.** duty를 명령 차원으로 열어도 도약을
유도하는 보상·태스크가 없으면 정책은 도약을 학습하지 않는다.
**도약은 명령 차원의 문제가 아니라 보상·태스크 설계의 문제다.**

## 1. 왜 "duty만 열기"가 안 되는가

WTW의 MoB(Multiplicity of Behavior)는 gait 파라미터를 명령으로 받되, **그 파라미터를
따르도록 강제하는 보상**이 함께 있어야 성립한다:

- `tracking_contacts_shaped_force` / `tracking_contacts_shaped_vel` (가중치 각 4.0)
  — 명령된 접촉 스케줄(`desired_contact_states`)을 따르도록 발의 힘·속도를 성형
- `_step_contact_targets`가 duty·phase·offset·bound로 접촉 스케줄을 생성

즉 duty를 열려면 **duty가 반영된 접촉 스케줄 + 그것을 따르게 하는 보상**이 필요하고,
그러면 **나머지 gait 차원과 기본 보행까지 같은 분포에서 다시 학습**해야 한다.
"duty만"으로 끝나지 않는다.

그리고 duty를 열어도 **도약은 별개다.** duty는 지지/체공 비율일 뿐, 몸통을 띄우는
추진력을 명령하지 않는다.

## 2. 기반: mujoco_playground Go1 (실측)

`locomotion/go1/joystick.py` 현황 — 여기서 출발한다.

| 항목 | 값 |
|---|---|
| 명령 | **3D** (vx, vy, yaw), 진폭 `[1.5, 0.8, 1.2]`, 1차 Markov 재샘플 |
| 관측 | state **48D** (linvel3+gyro3+gravity3+jointpos12+jointvel12+last_act12+cmd3) / privileged 84D |
| 제어 | `ctrl_dt=0.02`, `sim_dt=0.004`, `Kp=35, Kd=0.5`, `action_scale=0.5`, `episode_length=1000` |
| 보상 | 16개 항 (tracking_lin_vel 1.0, tracking_ang_vel 0.5, orientation −5.0, feet_clearance −2.0, feet_air_time 0.1, …) |

**장점**: MJX 네이티브 → 학습·배포가 같은 시뮬레이터. DOF 순서·actuator_net·solver
불일치 문제가 **구조적으로 사라진다.** Isaac Gym 불필요, Colab GPU에서 바로 돌아간다.

## 3. 단계별 계획

### B0. 명령 공간 확정 (설계 결정)

지형별 필요에서 역산한다. **차원마다 obs +1, 추종 보상 +1, 샘플 복잡도 증가**이므로
"있으면 좋은 것"이 아니라 "없으면 그 지형을 못 넘는 것"만 넣는다.

| 차원 | 필요한 지형 | 대안 없나? |
|---|---|---|
| vx, vy, yaw | 전부 | 필수 |
| height | 터널 | 없음 → 포함 |
| footswing | 턱, 틈 | 없음 → 포함 |
| **jump (트리거)** | 넓은 틈 | **§B4 — 이게 핵심 리스크** |
| stance_width | 외나무다리, 좁은 틈새 | HLC가 vy로 정렬 대체 가능? → 후순위 |
| pitch | 경사 | 자세는 정책이 알아서 잡을 수도 → 후순위 |
| duty/gait | (도약 보조) | **단독으로는 도약을 못 만든다. 후순위** |

→ 권장 최소 집합: **vx, vy, yaw, height, footswing, jump** = 6D

### B1. 환경 골격
playground Go1 base 재사용 + 명령 공간 확장 + 관측 확장 + 추종 보상 추가.
기존 16개 보상은 그대로 두고 새 차원의 추종 보상만 더한다.

### B2. 회귀 기준선 ★게이트★
**3D 속도만으로 playground 원본과 동등한 성능**을 먼저 재현한다.
이걸 못 하면 이후 단계의 실패 원인을 구분할 수 없다.

### B3. 차원 순차 확장
`height → footswing` 순으로 하나씩 열고 **매 단계마다 이전 차원 성능 회귀 검사**.
WTW가 겪었듯 차원을 늘리면 기본 보행이 나빠지는 일이 흔하다.

### B4. 도약 ★진짜 리스크★

두 갈래이며 **둘 다 성공 보장이 없다.**

**접근 ①: 명령 트리거 + 도약 보상**
- `jump` 명령이 1일 때 체공·정점 높이를 보상
- 장점: HLC가 명시적으로 "지금 뛰어"라고 지시 가능 (계층 구조에 부합)
- 위험: 보상 해킹(제자리 통통), 기본 보행 저하, 착지 실패

**접근 ②: 틈 지형 + 통과 보상 (parkour 방식)**
- 실제 틈 지형에서 "건너면 보상"으로 도약이 자발적으로 발현되게 함
- 장점: 연구 표준에 가깝고 실제로 잘 작동한 선례 다수
- 위험: **이건 사실상 지형 인지형 단일 정책이다** → §4의 아키텍처 문제로 직결

### B5. HLC 재통합
`policy.py`의 로드·추론 래퍼를 새 체크포인트로 교체. 인터페이스는 이미 있으므로 작다.

## 4. ⚠️ 반드시 함께 판단해야 할 것 — 계층 구조의 정당성

[02_hlc.md §0](../02_hlc.md)이 계층 분리의 근거를 이렇게 적어두었다:

> "성능이 아니라 **학습 예산·검증 용이성·LLC 재사용**을 위한 의식적 선택. 명령 병목(발
> 위치를 직접 명령 불가)이 성능 상한을 결정 — 극한 지형이 목표면 **인지형 단일 정책
> (관절 레벨)이 연구 표준**임을 인지한 상태의 트레이드오프"

**Plan B를 택하는 순간 세 근거 중 두 개가 사라진다.**
- "LLC 재사용" → LLC를 새로 학습하므로 소멸
- "학습 예산" → LLC 학습 비용이 추가되므로 소멸

남는 것은 "검증 용이성"뿐이다. 그리고 B4-②를 택하면 그것마저 인지형 단일 정책에 가까워진다.

→ **B를 진지하게 검토한다면 "차라리 단일 정책(D안)"과 나란히 비교해야 한다.**
Plan B의 비용 대부분(환경 구축, 보상 설계, 학습 인프라)은 D안과 공유된다.

## 5. 비용·리스크 요약

| 단계 | 성격 | 리스크 |
|---|---|---|
| B0~B2 | 기계적 | 낮음. playground 기반이라 예측 가능 |
| B3 | 반복 실험 | 중간. 차원 추가 시 기본 보행 저하 흔함 |
| **B4** | **연구** | **높음. 성공 보장 없음** |
| B5 | 기계적 | 낮음 |

**핵심**: B0~B3는 "하면 된다"에 가깝지만 **B4는 "될지 모른다"** 다.
그리고 B4 없이는 애초에 B를 할 이유가 없다(도약이 목적이므로).

## 6. 결정에 필요한 질문

1. **도약이 이 연구의 핵심 기여인가, 아니면 지형 돌파의 한 수단인가?**
   - 핵심이면 → B(또는 D). 수단일 뿐이면 → C(스코프 축소)
2. **step-over로 넘을 수 있는 틈 폭은 얼마인가?**
   → **답이 나왔다: 0.05 m** ([03_results.md §3](../03_results.md)).
   당시 "0.25~0.3 m면 실용적으로 충분할 수 있다"고 적었는데 실측은 그 1/5이다.
3. **계층 구조 자체를 재검토할 의향이 있는가?**
   - 있으면 B와 D를 같이 놓고 비교, 없으면 B4-①로 제한

⚠️ 2번의 답이 나온 지금, 이 결정은 **1번과 3번만 남았다.** 현재 노선은
[0001](0001-지형-돌파-폐기.md)의 C(스코프 축소)이며, P4/P5 결과를 보고 재검토한다.
