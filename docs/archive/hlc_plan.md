### 0.2 P0 복구 결과 (2026-07-28)

`.pyc`는 CPython 3.12로 컴파일됐고 로컬 환경은 3.10/3.11이라 완전 역마샬은 불가능했다.
대신 marshal 스트림에서 **심볼·상수 문자열을 추출**해 원본 구조를 회수했다:
`MJX_TO_WTW` / `WTW_TO_MJX` / `DEFAULT_DOF_POS_WTW` / `OBS_SCALES_*` / `COMMANDS_SCALE`,
그리고 `load_policy` → "Load PyTorch JIT policy and extract weights to JAX arrays",
`get_obs` → "Compute 70D observation vector". **원본도 JAX MLP 재구현 방식이었고,
`adaptation_module`은 빠져 있었다.**

체크포인트에서 확정한 실측 구조:

| 항목 | 값 | 근거 |
|---|---|---|
| 관측 | **70D** = proj_grav(3) + cmd×scale(15) + dof_pos_err(12) + dof_vel(12) + actions(12) + last_actions(12) + clock(4) | `legged_robot.py:302-338` |
| 히스토리 | 30 스텝, **오래된 것이 앞** (`cat(hist[num_obs:], obs)`) | `history_wrapper.py:23` |
| adaptation | 2100 → 256 → 128 → **2** (ELU) | `state_dict` 실측 |
| body | **2102** = 2100 + latent 2 → 512 → 256 → 128 → 12 | `state_dict` 실측 |
| **DOF 순서** | **FL, FR, RL, RR** ⚠️ URDF 파일의 joint 등장 순서(FR,FL,RR,RL)가 **아니다** | `legged_robot.py:878-902`의 자체 라벨 + gait 프리셋 정합성 + 폐루프 전수 조사 (`llc_port_debug.md`) |
| PD | Kp=20, Kd=0.5, sim dt 0.005, decimation 4 | `parameters.pkl` `Cfg.control` |
| 행동→목표각 | `a*0.25`, hip(0,3,6,9)만 ×0.5, + default_dof_pos | `_compute_torques:919-925` |

> ⚠️ **남아 있는 sim-to-sim 격차 ①**: WTW는 `control_type = "actuator_net"`(학습된 액추에이터
> 네트워크)을 쓰지만 MJX에서는 이상적 PD로 근사한다. 제거 불가능하며, 추종 오차가 남으면
> **1순위 용의자**다.

#### 0.2.1 MJX 성능 함정 (실제로 20분 행에 걸림)

Colab 첫 실행에서 `run_gate()`가 롤아웃 단계에서 20분 이상 멈췄다. 원인은 두 가지이며
둘 다 코드 쪽 문제였다.

**(A) menagerie `go1.xml`은 MJX용이 아니다.** 정확도 우선으로 작성되어 있다:

| 항목 | menagerie 기본값 | MJX용 |
|---|---|---|
| `opt.iterations` | **100** | 1 |
| `opt.ls_iterations` | **50** | 4 |
| `opt.cone` | elliptic | pyramidal |
| `opt.impratio` | **100** | 1 |
| 발 `geom_condim` | **6** | 3 |

MJX는 솔버 반복을 **컴파일 그래프에 그대로 펼친다.** 100 × 50이면 XLA 컴파일 자체가
수십 분이 된다 — 느린 게 아니라 아예 끝나지 않는 것처럼 보인다. `create_env(mjx_friendly=True)`
(기본값)가 위 표의 오른쪽으로 바꾼다. **접촉 해의 정확도가 낮아지는 근사**이며,
mujoco_playground의 사족보행 모델들이 쓰는 것과 같은 설정이다.
→ **sim-to-sim 격차 ②** 로 기록.

**(B) 롤아웃을 Python for 루프로 돌리면 안 된다.** 스텝마다 dispatch가 일어나고,
중간에 `np.asarray(data.qpos)`로 값을 꺼내면 **매 스텝 host 동기화**까지 걸린다.
단일 env MJX는 스텝당 비용이 커서 이 조합이 수십 분으로 불어난다.
→ `policy.make_rollout_fn()`이 **T 스텝 전체를 `lax.scan` 하나**로 돌린다
(컴파일 1회, 디스패치 1회, 동기화 1회). 렌더링도 롤아웃 중이 아니라
**끝난 뒤 로그된 qpos에서 일반 MuJoCo로 재생**한다(`check.render()`).

> 📌 이 함정은 HLC 학습 env(P1)에도 그대로 적용된다. `nav_env.step`은 이미 `lax.scan`을
> 쓰지만, **모델 옵션은 `create_env`를 거치도록** 해야 하고 학습 루프 안에서 값을
> 꺼내 보는 코드를 넣으면 안 된다.

**(C) `implicitfast + iterations=1`은 쓰면 안 된다.** mujoco_playground의 사족보행 설정을
그대로 가져오려 했으나, 이 모델·게인(Kp=20/Kd=0.5) 조합에서는 **발산한다**(정적 유지
테스트에서 z가 112 m로 튐). **integrator는 menagerie 기본값인 Euler를 유지한다.**
solver iterations는 1~100 전 구간에서 안정적이었으므로 정확도·컴파일 시간 기준으로만
고르면 된다 (기본 4/8 = Isaac의 `physx.num_position_iterations = 4`에 맞춤).

#### 0.2.2 리셋 자세 — NaN 발산의 주원인

`mj_resetData`는 **모델 기본값**을 준다. Go1에서는 관절이 전부 0, 즉 **다리를 쭉 편 자세**로
base z=0.445이며 이때 **발이 지면을 4 mm 관통한다(ncon=4)**. WTW가 학습한 리셋 자세는
`Cfg.init_state`의 base z=**0.34** + `default_joint_angles`이고, 이 자세에서는 발이 지면 위
1.5~2.5 cm에 떠 있다(ncon=0).

```
[A] mj_resetData        z=0.445, 관절 0,       발 -0.004 관통, ncon=4   ← 학습 분포 밖
[C] WTW init_state      z=0.340, 관절 default, 발 +0.015 여유, ncon=0   ← 정답
```

정책만 놓고 보면 관절 0인 상태의 `dof_pos_err`가 최대 1.5 rad로 학습 중 본 적 없는 값이고,
액션은 `clip_actions=10` → `×0.25` = **±2.5 rad의 목표각 오프셋**까지 나올 수 있다. 여기서
물리가 터진다. (PD로 default 자세만 유지하면 두 초기 자세 모두 안정적이므로, 발산은
초기 자세 자체가 아니라 **초기 자세가 정책을 분포 밖으로 밀어낸 결과**다.)

→ `policy.reset_data(...)`가 WTW 리셋 자세로 초기화하고 `mj_forward` 후 `put_data` 한다.
**P1의 `nav_env.reset`도 반드시 이 자세를 써야 한다.**
게이트에도 회귀 검사를 넣었다 — `test_policy.py` [5]가 리셋 시 `ncon == 0`과 발 클리어런스를
확인하고, `mj_resetData` 기본값이 관통한다는 것을 음성 대조로 함께 검증한다.

로컬 게이트 `python -m wtw_nav.llc.test_policy` → **25/25 PASS**
(상수가 전부 `parameters.pkl` 유래임을 대조, MLP forward vs torch `max|diff| = 9.2e-05`,
adaptation module 누락 시 실패하는지 음성 대조, 관절 매핑, 70D 조립,
`proj_gravity == R^T·[0,0,-1]`를 MuJoCo `mju_quat2Mat`과 교차검증).

**P0 통과 (2026-07-28).** 최종 MJX(GPU) 실측: `vx=0.8 → 0.871`, `vy=0.4 → 0.480`,
`yaw=0.8 → 1.058`, `min_z=0.155`, 무낙상, `|a|max` 포화 없음.

### 0.1 디렉토리 구조의 전제 — Colab 워크플로 (확정)

현재의 `wtw_nav/` 패키지 + `notebooks/` 구조는 **Colab 실행을 위해 의도적으로 채택된 것이며, 본 계획은 이 구조를 유지·강화한다.** (`hlc_design.md` §8의 원안 `FSM/`은 폐기됨)

```
로컬(Windows, CPU)          Google Drive 동기화          Colab (A100/T4)
  wtw_nav/*.py  ──────────────────────────────────────▶  drive.mount()
  코드 편집·형상 검증                                      os.chdir(project_path)
                                                          sys.path.append(cwd)
  notebooks/*.ipynb ────────────────────────────────────▶ import wtw_nav.envs.nav_env
                                                          → 학습 실행 / 렌더링
```

이 구조가 강제하는 설계 규칙:

1. **루트 스크립트 금지.** 모든 로직은 `wtw_nav/` 안의 import 가능한 모듈에 둔다. 노트북은 마운트·설정·호출만 한다. (과거 루트 `wtw_mjx_core.py`/`train_hlc.py` 방식이 유실 사고를 낳았고, Colab에서 `sys.path` 취급도 불안정했다)
2. **셀 재실행 안전성.** ⚠️ **`%autoreload` 금지** — Colab은 Python 3.12인데 autoreload가 `imp`를 import 한다(3.12에서 제거됨). 대신 `from wtw_nav.dev import reload_wtw; reload_wtw()` 후 다시 import. 기존 객체는 옛 클래스에 묶여 있으니 재생성할 것. 반영 확인은 `check.version_check()`.
3. **체크포인트는 반드시 Drive에.** Colab `/content`는 런타임 종료 시 소실된다. `checkpoints/`를 프로젝트 폴더(= Drive) 아래로 고정한다. 과거 파라미터 유실이 실제로 발생한 지점.
4. **JIT 재컴파일 최소화.** Colab 세션 시간이 유한하므로 §3.3의 "geom 수 고정" 원칙은 성능이 아니라 **세션 시간 보호** 차원에서 필수다.
5. **노트북 3분할 유지**: `01` LLC 검증(렌더링) / `02` HLC 학습(장시간) / `03` 평가·시각화. 학습과 평가를 한 노트북에 두지 않는다 — 학습 셀 재실행 비용이 너무 크다.

따라서 §2의 모듈 배치는 이 구조를 그대로 따른다.

## 1. 액션 스페이스 재정의 — 체크포인트 실측 기반

### 1.0 근거 자료 (중요)

액션 범위의 **유일한 정답 근거는 체크포인트에 동봉된 자기 자신의 config**다. 리포지토리의
`scripts/train.py`는 "현재 리포에 들어있는 스크립트"일 뿐 이 가중치를 만든 config라는 보장이 없다.
실제로 확인한 파일은 두 개:

| 파일 | 알려주는 것 |
|---|---|
| `runs/.../025417.456545/parameters.pkl` | 이 가중치 학습에 실제로 쓰인 `Cfg.commands` 전체 |
| `runs/.../025417.456545/curriculum/distribution.pkl` | **커리큘럼이 실제로 도달(unlock)한 명령 영역** (iteration 49500) |

핵심 구분 — WTW의 명령 범위는 세 겹이다. 혼동하면 안 된다:
- `lin_vel_x = [-1.0, 1.0]` → 커리큘럼 **시작 영역** (초기 seed)
- `limit_vel_x = [-5.0, 5.0]` → 커리큘럼 **확장 상한** (도달 보장 아님)
- `distribution.pkl`의 weights > 0 → **실제로 학습이 도달한 영역** ← 이게 HLC 액션 범위의 근거

| 12 | `stance_width` | `[0.10, 0.45]` 전 구간 | ✅ 연속 |
| 13 | `stance_length` | `[0.35, 0.45]` 전 구간 | ⛔ 고정(설계대로) |
| 14 | `aux`/compliance | `[0, 0.01]` | ⛔ 고정 0 |

> **duty / roll에 대하여** — WTW의 *명령 인터페이스*는 확실히 15D이고 duty와 roll을 포함한다
> (`command_scale_guide.md`가 맞다). 문제는 인터페이스가 아니라 **가중치**다. 공개된
> `pretrain-v0` 체크포인트는 이 두 차원을 상수로 박은 채 학습됐다 —
> `parameters.pkl`의 `gait_duration_cmd_range=[0.5,0.5]`, `body_roll_range=[-0.0,0.0]`.
> 논문/영상에 나오는 duty 스윕 시연은 별도 config로 학습된 다른 정책이다.
> **인터페이스에 슬롯이 있다는 것과 그 슬롯이 학습됐다는 것은 별개다.**
>
> 대응: (A) duty/roll 없이 진행 (권장, 재학습 0시간) — 설계 문서 §0의 점프 레시피에서
> "duty↓" 항목만 제거. (B) duty/roll을 열어 WTW LLC 재학습 (설계 로드맵 Phase 0 원안, 비용 큼).
> **(A)로 진행하고, P0.5에서 점프가 실제로 불가능하다고 판정될 때만 (B) 검토.**

### 1.2 vx–yaw 결합 제약 (독립 상자가 아님)

`distribution.pkl` iteration 49500의 unlock 맵 (행=vx, 열=yaw, 21×21 bin, `#`=학습 도달):

```
[trot]  104/441 unlock                    [pronk]  70/441 unlock
  vx -2.381 ..........###........           vx -1.905 ........#####........
  vx -1.905 ........######.......           vx -1.429 .......#######.......
  vx -1.429 ......#########......           vx -0.952 ......#########......
  vx -0.476 ...##############....           vx  0.000 ......#########......
  vx +0.000 ...##############....           vx +0.952 ......#########......
  vx +0.952 ....############.....           vx +1.429 .......########......
  vx +1.905 .......######........           vx +1.905 ........#####........
  vx +2.381 ........####.........
  marginal: vx±2.38, yaw[-3.33,+2.86]      marginal: vx±1.91, yaw±1.91
```

**마름모꼴** — 직진이 빠를수록 회전 여유가 줄어든다. 상자형 클리핑으로는 표현할 수 없다.

권장 처리: 액션을 상자로 매핑한 뒤 **L1 결합 제약을 한 번 더 건다.**
```python
s = |vx| / VX_MAX + |yaw| / YAW_MAX
scale = min(1.0, 1.0 / s)          # 마름모 밖이면 원점 방향으로 축소
vx, yaw = vx * scale, yaw * scale
```
- trot 전용 단계: `VX_MAX = 1.9`, `YAW_MAX = 2.4`
- pronk를 포함하는 단계: `VX_MAX = 1.4`, `YAW_MAX = 1.4` (pronk 마름모 내부에 완전히 포함)

> 📌 **앞선 오판 정정**: 초기 검토에서 `nav_env.py:39`의 vx scale `1.5`를 "LLC 훈련 상한 1.0 초과"로
> 지적했으나 이는 **틀렸다**. 1.0은 커리큘럼 seed일 뿐이고 trot의 실제 도달 범위는 ±2.38이다.
> **vx=1.5는 안전 구간 안이다.** 진짜 위험은 절대값이 아니라 vx와 yaw를 동시에 크게 주는 것.

> ⚠️ **미소 명령 데드존**: `legged_robot.py:822`가 `‖(vx,vy)‖ ≤ 0.2`인 명령을 **0으로 만든 뒤** 학습했다.
> 즉 0 < ‖v‖ < 0.2 구간은 LLC가 본 적이 없다. HLC 액션 매핑에서 이 밴드를 0으로 스냅할 것.

### 1.3 gait는 연속 차원이 아니라 **이산 선택 4종**

`parameters.pkl`의 `binary_phases: True` → `legged_robot.py:814-817`이 명령을 양자화한다:
```python
commands[5:8] = (torch.round(2 * commands[5:8])) / 2.0 % 1     # → {0.0, 0.5}
```
따라서 `(phase, offset, bound)`는 `{0, 0.5}³`의 꼭짓점에서만 학습됐고, 실제로는 4개 프리셋만 사용됐다
(`legged_robot.py:765-781`의 gaitwise curriculum). **중간값(예: phase=0.25)은 LLC가 한 번도 본 적 없다.**

- 그러므로 **trot↔pronk 연속 보간(`gait_morph`)은 분포 이탈이며 폐기한다.**
- gait 액션은 **로짓 4개 → argmax(추론) / Gumbel-softmax(학습)** 또는 더 단순하게
  **로짓 2개(trot vs pronk)** 로 구성한다. Brax PPO는 연속 액션 전제이므로,
  1차 구현은 **스칼라 1개 + 하드 임계**(`g > 0 ? pronk : trot`)로 시작하고,
  gradient가 죽는 게 확인되면 Gumbel-softmax로 승격한다.
- HLC 스텝이 10 Hz라 이산 전환의 채터링 위험이 있다 → **최소 유지 시간(예: 5 HLC step) 히스테리시스** 필수.

> ⚠️ **`(0.5, 0.5, 0.5)`는 어떤 프리셋도 아니다** — `nav_env.py:30`의
> `base_commands`가 `cmd[5:8] = (0.5, 0.5, 0.5)`로 되어 있다. `{0,0.5}³` 꼭짓점이긴 하나 4개 프리셋에
> 속하지 않는, 학습 중 거의 나오지 않은 조합이다. **트로팅은 `(0.5, 0.0, 0.0)`.** 최우선 수정 대상.
>
> ⚠️ **프리셋 이름 충돌**: `play.py:102`는 `bounding=[0,0.5,0]`, `pacing=[0,0,0.5]`라 하는데
> `legged_robot.py:774-781`의 생성 로직은 `pace→(0,0.5,0)`, `bound→(0,0,0.5)`로 **정반대**다.
> P0.5에서 영상으로 실제 발놀림을 보고 판정할 것. (trot/pronk는 양쪽 일치하므로 영향 없음)

### 2.1 `llc/policy.py` — P0 복구


> ⚠️ **정책은 모듈 2개다.** 공식 `go1_gym_deploy/scripts/deploy_policy.py:59-66`:
> ```python

  명령 인덱스 해석은 :239-247)에 있으며, `durations = commands[:, 8]`로 우리 인덱스 맵과 일치한다.
- torch JIT 모델을 JAX 안에서 직접 못 돌리므로, **가중치를 추출해 순수 JAX MLP로 재구현**하는 경로를 권장(`ac_weights_last.pt`). 그래야 `jit`/`vmap`/`scan` 안에 넣을 수 있고 2048 env 병렬이 가능하다. (torch 콜백 방식은 병렬 학습 불가.)
- **검증**: 동일 입력에 대해 torch 출력 vs JAX 출력 max abs diff < 1e-4.

| 높이 스캔 | 각 질의점 (x,y)에 대해 모든 box의 상면 z를 `where(inside_xy, top_z, -inf)` → `max` | 9×7=63 (초기엔 7×5=35로 시작) |

## 3. env 파이프라인 설계

### 3.1 JAX 제약 — 현 `nav_env.py`의 치명적 결함

`reset()` 내부에서 `mujoco.MjData(...)` / `mjx.put_data(...)`를 호출한다(`nav_env.py:43-45`). 이건 **Python 부수효과라 `jit`/`vmap` 안에서 동작하지 않는다.** 2048 env 병렬 리셋이 불가능하다.

**수정**: `__init__`에서 `mjx_data` 템플릿을 1회 생성해 보관하고, `reset`은 그 템플릿의 `qpos`/`qvel`만 `replace`한다.
```python
# __init__
self._init_data = mjx.put_data(self.mj_model, mj_data)   # 1회
# reset
data = self._init_data.replace(qpos=qpos, qvel=qvel)
data = mjx.forward(self.mjx_model, data)                  # kinematics만으로는 부족
```
`mjx.kinematics`가 아니라 `mjx.forward`를 써야 첫 관측의 접촉/센서 값이 유효하다.

### 3.2 스텝 구조 (10 Hz HLC / 50 Hz LLC)

```
HLC step:
  a9 ──▶ action_to_command ──▶ cmd15 (이 스텝 동안 고정)
      ──▶ lax.scan(llc_step_fn, ×5)      # 50Hz LLC, 내부 physics dt는 모델 설정 따름
      ──▶ sensors(new_data) + guidance ──▶ obs
      ──▶ reward / done
```
`decimation=5`는 config로. LLC 정책 주기(0.02 s)와 MJX `opt.timestep`이 일치하는지 **복구 시 확인**(WTW는 policy dt 0.02, sim dt 0.005 = 4 substep이 원본).

### 3.3 지형 랜덤화 = `randomization_fn`

병렬 env마다 지형이 달라야 하는데, 지형은 `mjx_model.geom_pos/geom_size`에 있다. Brax PPO는 이를 위해 `ppo.train(randomization_fn=...)` 훅을 제공한다(mujoco_playground `domain_randomize` 패턴).

```python
def domain_randomize(mjx_model, rng) -> (batched_model, in_axes)
#   geom_pos / geom_size 를 배치 축 있게, 나머지는 in_axes=None
```
**제약: geom 개수는 전 env 고정.** 따라서 코스는 "슬롯 M개 × 슬롯당 box 최대 B개"로 고정 배열을 만들고, 사용하지 않는 box는 지면 아래로 치워 무력화한다(`pos.z = -10`). 지형 종류 변경 = 파라미터 변경일 뿐 재컴파일 없음.
같은 파라미터 배열을 센서(§2.2)에도 그대로 넘겨 **물리와 센서가 항상 일치**하게 만든다. (과거 hfield 주입 시 물리/센서 불일치 문제가 있었음 — 이 설계로 원천 차단.)

### 3.3.1 ⚠️ brax 래퍼와 `lax.scan` 캐리 구조

brax PPO는 env state를 `lax.scan` 캐리로 쓴다. **`reset`과 `step`이 내는 `metrics`/`info`의
pytree 구조가 다르면** 다음으로 죽는다:

```
TypeError: scan body function carry input and carry output must have the same
pytree structure ... state.metrics is a dict with 5 children but ... 4 children,
symmetric difference of key sets: {'reward'}
```

원인: `step`에서 `metrics`를 **새 dict로 교체**하면 brax `EvalWrapper`가 끼워 넣은
`metrics['reward']` 키가 사라진다. 래퍼가 추가한 키를 보존해야 한다.

```python
metrics = dict(state.metrics)          # ← 교체하지 말고
metrics.update(progress=..., fell=...) #    갱신할 것
```

`info`도 같다 — `dict(state.info)`로 복사한 뒤 갱신해야 `EpisodeWrapper`의 `steps`·
`truncation`, `AutoResetWrapper`의 `first_pipeline_state`가 살아남는다.

→ `test_nav_env.py` [10]이 `brax_training.wrap()`과 `EvalWrapper`를 씌워 이 구조를
검사한다. 학습을 돌리기 전에 잡힌다.

### 3.4 관측 사양 (Phase별 누적)

| 구성 | 차원 | 도입 시점 |
|---|---|---|

### 3.4.1 학습 전 검증 순서 — 세 단계

학습을 돌리기 **전에** 세 가지를 순서대로 확인한다. 뒤로 갈수록 비싸므로 순서가 중요하다.

| 단계 | 명령 | 잡는 것 |
|---|---|---|
| 1 | `python -m wtw_nav.llc.test_policy` | LLC 상수·관측 조립·DOF 순서 (JAX 불필요) |
| 2 | `python -m wtw_nav.envs.test_nav_env` | **vmap 가능성**, brax 래퍼 pytree 구조, 차원·유한성 |
| 3 | `python -m wtw_nav.envs.scripted` | **env가 풀 수 있는 문제인가** + 타임아웃 여유 |

3단계가 특히 중요하다. 유도 벡터만 보는 단순 비례 제어기가 목표에 못 가면 성능이 아니라
**보상·종료·유도벡터가 틀린 것**이고, 그 사실을 30M 스텝 태운 뒤에 알아내는 것은 낭비다.

> 📌 **타임아웃 여유 (실측으로 잡은 문제)**: 기준 제어기(vx 1.0)가 20 m 코스를 **19.1 s**에
> 주파했는데 타임아웃이 20 s였다. 여유가 0.9 s뿐이면 **기준보다 조금만 느린 정책은 전부
> 타임아웃되어 도달 보너스를 한 번도 못 받는다** — 학습이 엉뚱한 이유로 실패한다.
> → `timeout_s`를 30 s로 올렸다. 정책은 vx를 1.9까지 낼 수 있어 원리상 10.5 s면 간다.
> `scripted.py`가 이제 여유를 자동으로 계산해 30% 미만이면 경고한다.

### 3.5 보상 / 종료

```python
r = 10.0 * (d_prev - d_now)        # progress (유도 방향 투영 거리)
  + 10.0 * reached                 # 도달 보너스
  - 0.01                           # 시간 페널티
  - 5.0  * terminated_bad          # 전복/추락/교착
  - 0.01 * ||cmd_t - cmd_{t-1}||²   # 명령 급변
  - 1.0  * body_contact            # 몸통/허벅지 접촉
done: 완주 | 전복(proj_grav_z > -0.5) | 추락(z < z_floor - 0.3) | 타임아웃(60 s = 600 step)
```
**핵심 메커니즘 유지**: 지형 돌파 기술은 `progress(건너려는 동기) × 추락 종료(어설픈 시도의 대가)`에서 나온다. 위험 지형에 별도 성형 보상을 주지 않는다.

### 3.4.2 ⚠️ PPO 하이퍼파라미터 — 조용히 실패하는 두 가지 (2026-07-29 실패 기록)

첫 P1 학습이 실패했다. 정점(655k 스텝, reward 46.3, dist 14.7 = 5 m 전진) 뒤
**단조 하강**해 끝에는 `len=30`(교착 최소 창), `dist=20.1`로 아예 안 움직였다.
`fell=0`이었으므로 물리·env 문제가 아니라 **학습 설정 문제**다.

**(가) 갱신 횟수가 실제 학습량이다.** brax는
`batch_size × unroll_length × num_minibatches` 만큼의 env 스텝을 모아야 정책을
**한 번** 갱신한다. 1024×20×32 = 655,360이면 예산 10M에서 갱신이 15회뿐이다.
로그에서 행 간격이 곧 이 값이므로 눈으로 확인할 수 있다. **수백 회가 필요하다.**

**(나) `num_evals`가 `num_timesteps`를 덮어쓴다.** eval마다 최소 1회 학습하므로
실제 스텝 >= `num_evals × env_step_per_training_step`. 40 × 655,360 = 26.2M이라
10M을 지정했는데 25.5M을 돌았다. eval 비용도 컸다 — 101분 중 18분.

**(다) 엔트로피 항이 정책 손실을 압도할 수 있다.** 실패한 실행의 진단:

```
training/policy_loss          = -0.00025
training/entropy_loss         = -0.05361      ← 200배
training/policy_dist_mean_std =  0.798        ← 끝까지 최대치 근처
```

`entropy_cost=1e-2`가 우리 보상 규모에 비해 컸다. 옵티마이저가 리턴이 아니라
엔트로피를 최대화하니 정책이 수렴하지 못하고 성능이 하강한다. **`policy_loss`와
`entropy_loss`의 비를 반드시 볼 것** — 이 둘이 같은 자릿수여야 한다.

**(라) 할인율은 에피소드 길이를 덮어야 한다.** γ=0.99는 유효 지평 100스텝(10 s)인데
코스 주파는 20~30 s다. 가치함수가 목표를 보지 못한다. γ=0.997 → 지평 333스텝.

수정 결과: 갱신 39회 → **183회**. `train._check_ppo_config()`가 (가)(나)를
학습 시작 전에 경고한다.

### 3.4.3 ★ 타임아웃을 `done`에 넣지 말 것 (brax truncation)

두 번째 실행은 **도달률 15.6%까지 갔다가** 무너졌다. 붕괴 시작점이 `len`이 상한
300에 닿은 직후와 정확히 일치했다. brax 0.14.1 `EpisodeWrapper.step`:

```python
state.info['truncation'] = jp.where(steps >= episode_length, 1 - state.done, zero)
```

env가 같은 스텝에 `done=1`을 세우면 `truncation = 0`이 되어 brax가 시간 초과를
**진짜 종료로 오인**하고 가치 부트스트랩을 0으로 자른다. "17 m 걸어왔고 아직 걷는
중"인 상태의 가치가 0이 되니, 오래 걷는 정책일수록 손해를 보고 학습이 짧은
에피소드로 붕괴한다. 시간 제한은 `train.py`가 `episode_length`로 넘겨
EpisodeWrapper가 처리하게 두는 것이 옳다.

부수 효과: `done`에서 타임아웃을 빼면 `dist * done` 지표가 시간 초과 에피소드에서
0이 된다. 지표 전용 `last`(타임아웃 포함) 플래그를 따로 쓸 것.

수정 후 붕괴가 사라졌다 — 6.5M 스텝 동안 `len≈300`, `dist` 1.2~6.4로 안정.
게이트 `test_nav_env` [11]이 이 불변식을 고정한다.

### 3.4.4 ★ 보상 유인의 **상대 크기**를 학습 전에 볼 것

세 번째 실행은 붕괴하지 않았지만 **도달률이 0.17에서 6.5M 스텝 동안 오르지
않았다.** 원인은 학습이 아니라 설계였다:

```
총 progress 보상 = 10 × (19.62 − 1.24) = 183.8
관측된 리턴      = 184.6      ← 리턴이 전부 progress
```

| 항목 | 리턴 대비 |
|---|---|
| 마지막 1.24 m를 마저 가서 도달 (+12.4 +10) | **11%** |
| 300스텝 시간 페널티 전체 (−3) | 1.6% |
| 100스텝 빨리 끝내기 (+1) | **0.5%** |

정책은 이미 얻을 수 있는 리턴의 97%를 확보했다. **마무리할 이유도 서두를 이유도
없었고**, 실제로 18.4 m를 30초에 걸쳐 0.61 m/s로 느긋하게 갔다(LLC는 vx=0.8에서
0.86 m/s를 낸다). 정책은 보상대로 행동했다.

수정: `reach` 10 → **100**, `time` −0.01 → **−0.05**. 마무리 유인 7% → **37%**.

**`python -m wtw_nav.envs.reward_audit`** 가 이 부류를 학습 전에 잡는다(JAX 불필요,
몇 초). 대표 시나리오의 리턴을 나열하고 ① 도달 vs 거의 도달 격차 ② 속도 유인
③ 순위 역전을 검사한다. 옛 상수를 넣으면 ①이 7%로 FAIL 난다.
**보상 상수를 건드릴 때마다 돌릴 것.**

### 4.1 ★ P2·P3 폐기와 범위 재정의 (2026-08-01)

gap 사다리 PPO 실측(`runs/p2_gap`, 6.9M 스텝)에서 **8D 명령이 사줄 수 있는 지형
능력이 3 cm**로 나왔다(`terrain/limits.py`). 대조군인 "고정 vx 최대 명령" 하나와
동일한 level 1이었다 — PPO가 8축을 동시에 굴려도 무식한 직진을 못 이겼다.

따라서 P2·P3의 게이트("각 지형 성공률 > 80%")는 **원리적으로 달성 불가**다.
남은 지형 4종을 재는 것은 "얼마나 못 넘나"를 4번 더 확인하는 일이므로 하지 않는다.

**범위를 이렇게 다시 정의한다:**

> 이 로봇에게 지형은 **넘을 대상이 아니라 피할 대상**이다.
> 연구의 본체는 지형 돌파가 아니라 **미로 주행(P4)** 이다.

이건 후퇴가 아니라 A안 결정 당시의 근거가 그대로 남는 쪽이다 — "센서·HLC 루프·
미로는 어느 안을 택하든 필요하다"고 적어 둔 그 부분이 본체가 됐을 뿐이다.

파생 결정:
- 센서는 **2D 라이다 16D 하나**로 줄인다. height_scan(35D)·ceiling_scan(5D)은
  넘을 수 있는 지형이 생기면 그때 만든다. 관측 21D -> **37D** (77D가 아니라).
- `hlc/fsm.py`는 쓰지 않는다. 전환할 지형별 명령 모드가 존재하지 않는다.
- ~~`limits.py`의 ledge/beam/tunnel/slope는 **미측정으로 남긴다.**~~ **철회됨
  (2026-08-07). 조건이 충족됐다** — "통과 가능한 지형을 미로에 넣고 싶다"는 요구가
  실제로 생겼고(§4.2), 재보니 **slope·tunnel·rough는 통과 가능했다.** 즉 위의
  "남은 4종을 재는 것은 얼마나 못 넘나를 4번 더 확인하는 일" 이라는 예측은
  **틀렸다.** gap 하나의 결과를 지형 일반으로 확대한 것이 오류였다 — gap은
  "지면이 없는" 유일한 지형이라 가장 불리한 표본이었다.

### 4.2 지형 실측 기록 (2026-08-06 ~ 08-09)

**측정 원칙**: PPO 이전에 **고정 명령 대조군(A)** 부터 잰다. 대조군이 곧 하한이고,
PPO는 그 위를 얼마나 올리는지로만 평가한다. 값의 단일 진실 공급원은
`terrain/limits.py`이며 **여기는 그 값이 나온 경위**를 남긴다.

공통 장치: `terrain/modules.ladder()` (난이도를 코스 x축에 배열) +
`envs/scripted.evaluate()` (시드별 `level` = 넘긴 장애물 수) + 매 실험 영상.

| 지형 | 실측 | 설계값(여유) | 시드 | 상태 |
|---|---|---|---|---|
| `gap` | **0.05 m** | 0.035 (×0.7) | PPO 6.9M + A | 확정 |
| `slope` | **20°** | 14 (×0.7) | 3 | 확정 |
| `tunnel` | **0.291 m** | 0.335 (×1.15) | 3 | 확정 |
| `rough` | **0.06 m (진폭)** | 0.042 (×0.7) | 5 | 확정 |
| `ledge` | **0.07 m** | 0.049 (×0.7) | 위상 8 | 확정 |
| `beam` | 기하 0.321 m / 벽 0.55 | — | 3+5 | ★ **제외 확정** (§4.2e) |
| `jump` / `slit` | — | — | — | 영구 제외 |

★ **네 지형 전부에서 낙상이 0건이다.** 한계를 정한 것은 매번 전복이 아니라
**추진 정지(slope) · 명령 포화(tunnel) · 해가 명령 공간에 없음(gap)** 이었다.
이건 설계에 그대로 쓰인다 — 미로에서 위험한 것은 "넘다가 넘어짐"이 아니라
**"넘지 못하고 갇힘"** 이므로, 종료 조건은 낙상이 아니라 교착을 잡아야 한다.

#### (a) 경사 20° — ★ **내 가설이 반증됐다**

1차 측정에서 24°에 막혔는데, 그때 로봇이 **−126° 회전하고 y로 −1.55 m 표류**해
있었다. "지형이 아니라 내 제어기가 만든 한계"라는 유보를 달아 뒀다.
`guidance.heading_hold`와 같은 법칙을 `scripted.guidance_controller`에 넣고
(`hold=1`) A/B로 다시 쟀다:

| | level(pitch 0.0) | level(pitch 0.3) | 종료 yaw | 종료 y | 최대 x |
|---|---|---|---|---|---|
| `hold=0` | 2.00 | **3.00** | −126° | −1.55 | 12.39 |
| `hold=1` | 2.00 | **3.00** | **−0°** | **−0.07** | 12.43 |

진로 유지기는 완벽히 작동했다(회전·표류가 사라짐). **그런데 level이 같다.**
→ **회전은 원인이 아니라 결과였다.** 램프에서 먼저 막히고 그 다음 돌아선 것이다.
20°를 확정하고 유보를 뗐다. **같은 논리로 `gap` 0.05에 달아 둔 유보도 철회한다.**

참고로 마찰 상한은 `atan(0.6) = 30.96°`이고, WTW 학습 시 중력 랜덤화
(`gravity_range=[-2,2]`)의 실효 기울기가 평균 8.97° / p90 13.3°다. 실측 20°는
**학습 분포의 p90보다 위**다 — 즉 경사는 학습된 강건성이 잘 외삽된 경우다.

#### (b) 터널 0.291 m — ★ **평지 예측이 실지형에서 정확히 맞았다**

지형을 만들기 전에 **평지에서** `scripted.body_clearance()`로 명령별 로봇
최고점을 쟀다. 그 값으로 사다리 결과를 예측하고, 그 다음 실지형을 돌렸다:

| height 명령 | 평지 최고점 | 예측 level | **실측 level** |
|---|---|---|---|
| −0.22 | 0.291 m | 5 | **5.00** ✓ |
| 0.00 | 0.337 m | 4 | **4.00** ✓ |

⚠️ `_geom_top`은 **회전을 반영한 형상별 z반경**을 쓴다. `geom_rbound`를 쓰면 몸통
박스가 반경 0.20으로 잡혀 실제 윗면(중심+0.057)의 3.5배가 되고 예측이 통째로
틀린다. 이 예측 적중은 그 구현이 맞았다는 증거다.

⚠️ **두 개의 수가 있다.** `height=-0.08`(최고점 0.320 > 천장 0.30)도 level 5를
냈다 — 천장에 **닿고도 비벼서 밀고 나갔다**. 설계에는 **접촉이 없는 0.291**을 쓴다.

★ 이 "평지에서 재고 → 예측하고 → 실지형으로 확인" 절차는 `beam`에 그대로 재사용한다(§4.3).

#### (c) 요철 진폭 0.06 m

`_rough_patch`: 중앙 띠(반폭 1.0 m)에 `nx × 6` 격자 박스, 윗면 z를 U(−a,a)로
흔든다. 양옆은 평평한 슬래브(표류해도 낙하하지 않도록).

세 번 고쳐서야 유효한 측정이 됐다. **세 번 다 "실패가 성공처럼 보이는" 종류였다:**

1. **레인 3개(홀수) → 롤 교란 0.** 가운데 레인이 y=0에 걸터앉고 그 폭 0.667 m가
   `stance_width` 최대 0.42 m보다 넓어 **좌우 발이 항상 같은 타일**을 밟았다.
   짝수(6)로 바꿔 레인 경계를 정확히 y=0에 놓았다. `ValueError` 가드를 넣었다.
2. **첫 사다리(0.02~0.07)가 너무 쉬웠다** — level 5.33, 여러 축이 6.00(완주)으로
   천장을 쳤다. 원인은 "단차 = 2×진폭"이 **최악값**이었다는 것. 이웃 타일이 독립
   U(−a,a)면 단차는 삼각분포라 **평균 |Δ| = 2a/3**이고, `P(|Δ|>d) = (1−d/2a)²`다.
   a=0.07의 평균 단차는 0.047 m로 gap 실측 0.05와 같은 자릿수였다 — 통과가 당연했다.
   평균 단차 기준 등간격으로 재설계: `(0.06 … 0.21)`.
3. **띠를 벗어나 옆 평지를 밟았다** (영상에서 확인, y가 한 방향으로만 +0.12→+0.70).
   LLC의 요속 편향 ω≈0.118 rad/s가 **계통적**이라 매번 같은 쪽으로 샜다.
   → ★ **띠를 넓히지 않고 제어기를 고쳤다.** 넓히는 것은 geom을 2배로 늘리면서
   원인(되먹임 부재)은 그대로 두는 증상 대처이고, 표류가 시간에 2차로 자라므로
   어떤 폭도 충분하지 않다. `hold=1` + **이탈 비율을 매 실행 계측**
   (`scripted._report_off_band`).

최종: n=5, `hold=1` → **level 1.40** (2,2,1,1,1). 0.06은 5/5, 0.09는 2/5 통과.
띠 이탈 1%, |y|max 1.10 — 오염 없음. `rough_report()`가 단별 타일 72개와
윗면 z 폭 0.119~0.419(= 2×진폭)를 모델에서 직접 읽어 확인했다.
`hold=0`도 1.33으로 거의 같다 — 요철에서는 표류가 실패 원인이 아니었다.

★ 오염된 1차 사다리와 **모순되지 않는다**: 둘 다 벽이 a=0.07과 0.09 사이임을
가리킨다. 독립적인 두 사다리가 같은 곳을 짚었다.

⚠️ **`rough` 평균 단차(0.040)와 `gap`(0.05)을 같은 척도로 비교하지 말 것.**
틈은 지면이 없어 발이 빠지고, 요철은 지면이 있어 다리 PD가 흡수한다.

#### (d) 턱 0.07 m — ★ **"LLC로는 턱을 못 넘는다"가 반증됐다**

`scripted.phase_sweep`, 위상 8점 × 시드 1. 사다리 `(0.03 … 0.17)` 증분.

| 증분 | 누적 | 도달 | 조건부 성공률 |
|---|---|---|---|
| 0.03 / 0.05 / **0.07** | 0.03 / 0.08 / 0.15 | 8 | **100%** |
| 0.10 | 0.25 | 8 | 75% |
| 0.13 | 0.38 | 6 | 33% |
| 0.17 | 0.55 | 2 | 0% |

**0.07 m는 8/8이다.** 사전 예측 구간(0.05~0.10)이 맞았고, `gap` 0.05 <
`ledge` 0.07 < `rough` 최대단차 0.12 순서도 물리적으로 일관된다 — 지면이 있으니
틈보다 낫고, 요철은 오르내림이 상쇄되니 턱보다 낫다.

★ **위상이 지배 변수임이 확인됐다.** level이 3~5로 흩어졌다(폭 2). 평균 level로
기록했으면 틀렸을 값이고, `rng_seed` 대신 `x0`를 흔든 설계가 정당했다.

★ **`footswing`은 완전히 무력했다.** 0.32로 올려도 위 표 여섯 줄이 **전부 동일**하다.
그런데 개별 위상 결과는 바뀐다:

```
A0        5 5 4 4 4 3 3 4     정렬 -> 3,3,4,4,4,4,5,5
fs=0.32   4 4 3 3 5 5 4 4     정렬 -> 3,3,4,4,4,4,5,5     ← 다중집합이 같다
```

즉 발을 높이 드는 것은 **어느 위상이 성공하는지**를 바꿀 뿐 **얼마나 자주
성공하는지**는 못 바꾼다. 실패 원인이 발 높이 부족이 아니라는 직접 증거다.

#### (e) 외나무다리 — 발 간격 확정, 폭은 재측정 필요

**① 발 간격(`scripted.foot_track`, 평지, 시드 3):**

| sw 명령 | W_foot | 구간 이득 dW/dcmd | 표류 D |
|---|---|---|---|
| 0.12 | **0.275** | — | 0.179 |
| 0.24 | 0.334 | 0.62 | 0.263 |
| 0.42 | 0.520 | 1.12 | 0.753 |

★ **비대칭 포화다.** 넓히는 쪽은 1:1로 듣는데(이득 1.12) 좁히는 쪽은 1/3만
듣는다(0.37). 중립(0.25, W_foot≈0.34)에서 하한까지 끝까지 좁혀도 0.065 m(19%)뿐이다.
→ **발 간격의 바닥은 0.275 m**, 기하 바닥(다리 전폭) = 0.275 + 2×0.023 = **0.321 m**.

★ **표류가 발 간격과 같이 커진다** (0.179 → 0.753). 외나무다리에서 `stance_width`를
넓히는 것은 기하로 얻고 항법으로 잃는 게 아니라 **양쪽 다 손해**다.

**② hold A/B — 경사와 정반대다:**

| | level | 벽 | 다리 밖 착지 |
|---|---|---|---|
| `hold=1` | **5.00** (5/5) | 0.49~0.60 | 0.5% |
| `hold=0` | **2.00** (5/5) | 0.88~1.06 | 0.8% |

진로 유지기 하나가 벽을 **0.88 → 0.55로 40% 밀었다.** 경사에서는 같은 장치가
level을 전혀 바꾸지 못했다(2.00/3.00 동일).

> **경사는 추진 한계, 외나무다리는 항법 한계다.**

★ 그래서 `modules.beam()`의 "열린 루프로 재라"는 옛 원칙을 철회한 것이 옳았다.
그대로 뒀으면 **0.88을 "LLC의 한계"로 기록**했을 텐데 실제로는 0.55다 — 60%
과대평가할 뻔했다.

**③ ⚠️ 그런데 이 0.55는 아직 확정할 수 없다. 두 가지 결함이 있었다:**

- **`need` 공식이 코스 길이에 의존했다.** `need = 2×(max|y_foot,world| + r)`로
  월드 좌표를 썼는데 거기엔 표류가 섞여 있고, 표류는 거리에 따라 자란다 —
  평지 10 m에서 D=0.179였던 것이 사다리 21 m에서 0.350이 됐다. 로봇의 성질이어야
  할 수가 코스 길이에 따라 변하면 설계에 쓸 수 없다.
  → **기하(길이 무관)와 표류(길이 의존)를 합치지 않는다.** `foot_track`은 이제
  `floor = W_foot + 2r`와 `D`를 따로 낸다.
- **다리 *사이*가 전폭 12 m였다** (`_slab`이 `PLATFORM_W=6.0`을 반폭으로 쓴다).
  다리마다 3 m짜리 자유 표류 구간이 있어서, 로봇은 거기서 밀린 채 다음 다리에
  도착한다. 즉 사다리가 잰 것은 "얼마나 좁은 다리를 걷나"가 아니라 **"12 m
  벌판에서 얼마나 직진하나"** 였다. 영상에서 "폭은 넉넉한데 직진이 안 돼서
  떨어진다"로 보인 것이 이것이다.
  → `BEAM_APPROACH_W = 2.0`(미로 통로 폭)으로 좁히고, `_report_off_beam`이
  표류를 **다리 위에서만** 재도록 고쳤다.

**④ 재측정 결과 — ★ `beam` 제외 확정 (2026-08-09):**

사다리 `(0.80, 0.64, 0.55, 0.45, 0.39, 0.32)`, 통로 폭 2 m, 시드 5.

★ **몸 중심이 다리 밖으로 나간다. 발은 다리 위에 있었다.** 즉 이 사다리가 재고
있는 것은 다리 폭이 아니라 **진로 유지기의 정상상태 오차**다.

그리고 그 오차는 게인 문제가 아니라 **구조다**. `heading_hold`는 적분항이 없는

    y_ss = ω / (k_psi · k_y) = 0.118 / (1.5 × 0.5) = 0.157 m

관측 0.297의 절반이 이 항이다. 게인을 올리면 줄지만 0이 되지 않는다.

⇒ **`slit`과 같은 부류다**(횡방향 정밀 정렬 요구 > 고유 표류). 미로에 넣지 않는다.

그리고 그때도 고정 게인 스크립트가 아니라 **P4에서 학습된 HLC로 재는 것이 맞다** —
지금 기록하면 로봇의 값이 아니라 내 제어기의 값이 된다.

### 4.4 ★ P4 미로 학습 — **게이트 통과 (2026-08-10)**

`runs/p4_maze`, 5,898,240 스텝, 5×5 seed 0, 2048 env, 234분.

| | 시작 | 최종 | 게이트 |
|---|---|---|---|
| **도달률** | 0.000 | **0.992** | > 0.70 ✅ |
| 남은거리 | 11.200 | 0.029 | — |
| 낙상 | — | 0.008 | — |
| 에피소드 길이 | 160 스텝 | **91 스텝 (9.1 s)** | — |

★ **PPO가 스크립트 제어기(14.4 s)보다 1.6배 빠르다.** 되먹임을 배운 정책이 고정
게인 비례 제어기를 이기는 것이 정상이고, 실제로 그렇게 됐다. 낙상은 사실상 0이다 —
지형 실측 6종에서 낙상이 한 건도 없었던 것과 같은 그림이다.

**학습 전 게이트 둘을 먼저 통과시켰고, 그것이 이 실행이 한 번에 된 이유다.**

- **게이트 ① broadphase 근사 검증** — `max_geom_pairs=0/32/64` A/B (§8.3.2).
  5시드 중 4개가 소수점까지 동일. k를 32→64로 올려도 기준에 **가까워지지 않았고**
  (시드 0이 오히려 0.1 s 멀어짐) 차이는 전부 HLC 1스텝 단위였다 → 접촉 손실이 아니라
  혼돈 발산. 영상에서 벽 관통 없음. **k=32 채택.**
- **게이트 ② env가 풀리는가** — 스크립트 제어기가 **5/5 도달**(14.1~15.7 s).
  흐름장·보상·종료가 전부 맞다는 뜻이다. P1에서 도달 불가능한 코스에 6.5M을
  태웠던 사고가 여기서 반복되지 않았다.

#### ⚠️ ETA 예측이 1.7배 낙관적이었다 — `bench`를 고쳤다

```
eval 간격 소요: [9.5, 9.5, 9.5, 9.5, 9.5, 9.5, 9.5, 9.5, 9.5] 분   ← 완전히 일정
정상상태 414 HLC steps/s   (bench 예측 719, ×0.58)
```

변동이 아니라 **상수 오차**다. `bench.breakdown`은 `jax.vmap(env.step)` 하나만 재고
그 위에 얹히는 것을 세지 않았다:

| | 규모 |
|---|---|
| PPO 갱신 | `num_updates_per_batch 4 × num_minibatches 8` × eval구간당 6갱신 = **192회 그래디언트** |
| brax eval | 24회 × `episode_length` 스텝. **`PPOConfig.num_evals` 주석에 이미 "101분 중 18분"으로 기록돼 있었다** |
| AutoReset·Episode 래퍼 / 관측 정규화 | raw `env.step`에는 없음 |

분해하면 **eval ~18% + 갱신 ~30% = 42%**이고, bench가 달고 있던 "20~40% 더 걸립니다"는
**갱신만 세고 eval을 빼먹은 값**이었다. → 실측 계수 **×0.58**을 넣어 raw와 실제를
두 줄로 내게 고쳤다. 첫 eval 구간만 11.9분(+2.4분)인 것은 **학습 스텝 그래프의
별도 컴파일**이다 — eval 그래프 컴파일(3.9분)과 다른 단계다.

#### ★ 예산의 절반이 낭비였다

| 스텝 | 경과 | 도달률 |
|---|---|---|
| 983k | 44분 | 0.617 |
| **2.46M** | **101분** | **0.961** |
| 4.42M | 177분 | 0.992 |
| 5.65M | 225분 | 0.992 (진동) |

**최고점의 95%에 2.46M(전체의 43%)에서 닿았고, 나머지 3.4M(140분)이 산 것은 3%p다.**
다음 실행은 `num_timesteps ≈ 3.2M`이면 충분하다. `eval.curve()`가 이 무릎점을
자동으로 찾아 권장값을 낸다.

⚠️ 반대로 `num_evals=25`는 유지할 값이다. eval이 18%를 먹지만 **9.5분마다 곡선을
본 덕에** 이 수렴 판단이 가능했다. 10으로 줄였으면 못 봤다.

#### 남은 것 — 일반화 (P5)

★ 미로 하나는 MJX 모델 하나이므로 **학습 seed의 99.2%는 레이아웃 암기와 구분되지
않는다.** 관측 37D에 절대좌표도 맵 크기도 없으니(`nav_env._obs`) 원리적으로는

⚠️ 큰 미로에서 떨어지면 **먼저 의심할 것은 유도벡터 `d_norm`**이다 — 관측 중 유일하게

### 4.3 남은 2종의 실험 설계 (2026-08-09 확정, 미실행)

#### `beam` — 재는 것은 다리 폭이 아니라 **발 간격**이다

질문을 바꾼다: "외나무다리를 건널 수 있나"가 아니라 **"발을 얼마나 좁힐 수 있나"**.
터널에서 통한 절차(§4.2b)를 그대로 쓴다 — **평지에서 재고, 예측하고, 확인한다.**

두 수를 **분리해서** 잰다. 이것이 "발 간격 탓인지 항법 탓인지"의 판별 장치다:

- `W_foot(stance_cmd)` — 평지에서 `stance_width` 0.12→0.42 스윕, **네 발 geom의
  실제 y 극값**. (`body_clearance`의 대칭물 `foot_track()`)
  ⚠️ `body_height`가 그랬듯 **포화를 예상한다** — 명령 0.12를 준다고 발이 0.12로
  모이지 않을 수 있다. **그 포화 곡선 자체가 산출물**이다.
- `D` — 같은 주행의 `max|y_body|` (`hold=1`). 항법의 순수 능력치.

예측: 최소 다리 폭 = `W_foot + 2D + 2r_foot`. 사다리는 이 값 주변으로 다시 잡는다
(현 프리셋의 2.0 m는 `ROUGH_HALF_W`의 2배로 사실상 평지다).

| 관측 | 결론 |
|---|---|
| 실패 폭 ≈ `W_foot + 2D` | 예측대로 — 둘의 합이 한계 |
| 실패 폭 ≈ `W_foot`, `max\|y\|` 작음 | **발 간격이 한계** (항법 무죄) |
| 실패 폭 ≫ `W_foot`, `max\|y\|` 큼 | **항법이 한계** |
| 발이 다리 밖을 밟은 스텝 존재 | 착지 위상 문제 |

⚠️ `modules.beam()` docstring의 "**측정 중 표류를 보정하지 않는다**(열린 루프)"는
**철회한다.** 근거였던 "보정을 넣으면 내 보정기 성능을 재게 된다"는 경사 A/B에서
반증됐다(`hold` 0/1이 동일 level). 열린 루프로 재면 LLC 능력이 아니라 이미 아는
계통 편향 ω=0.118을 재게 된다. **`hold=1`로 재고 열린 루프는 대조군 1회.**

#### `ledge` — 결정적 값이 아니라 **성공 *확률*** 을 잰다

LLC는 `measure_heights=False`라 지형을 못 본다. 그래서 턱 앞 도착 시의 **보행 위상**이
제어 불가능한 난수이고, 같은 명령·같은 높이여도 결과가 갈린다.
→ 위상은 스윕 대상이 아니라 **샘플링 대상**이다. 명령을 고정한 채 **턱 시작 x를
1 stride 안에서 균등하게 흔든다**:

```
stride = vx / step_freq = 1.0 / 3.0 = 0.333 m
x0 ∈ 3.00 + {0, 1/8, …, 7/8} × 0.333      (위상 0~360°를 8분할)
```

기존 `rng_seed` 스윕은 초기 자세 잡음만 흔들어 위상을 덮지 못했다.

조합 폭발은 없다. 물리적으로 관계있는 축이 `footswing`·`step_freq`·`height`
셋뿐이고(`vy`/`yaw`/`stance_width`는 무관, `pitch`는 경사 전용), 1D 스윕으로
충분하다 — **8축 조합 탐색은 원래 PPO의 일**이다(`ladder()` 설계 근거 ③).
어떤 축도 안 먹으면 그 자체가 "LLC 재학습이 필요하다"는 결론이다.

- A0: 중립 명령 × 위상 8 → 높이별 성공률 (**바닥**)
- A1: `footswing` (0.05/0.12/0.20/0.32) × 위상 8
- A2: A1 최적 고정 후 `step_freq`(2.1/3.0/3.9), `height`(−0.22/0/+0.13) 각 1D
- 총 88 롤아웃. 요철 사다리 1회분과 비슷하다.
- ★ 기록은 **평균 level이 아니라 성공률 분위수**로 한다. 위상 난수 때문에 평균은
  설계에 쓸 수 없다.

⚠️ **현 프리셋 `(0.03, 0.03, 0.03, 0.04, 0.04, 0.05)`는 못 쓴다.** 1~3단이 동일
난이도라 사실상 3점만 구분하고, 그 전 구간이 요철이 이미 통과시킨 0.04 아래다 —
요철 1차 사다리와 같은 천장 치기를 반복한다. 등간격으로 재설계:
`(0.03, 0.05, 0.07, 0.10, 0.13, 0.17)`.

**"LLC만으로는 턱을 못 넘는다"는 아직 말할 수 없다.** 요철 a=0.06을 5/5 통과했고
그 지형의 단차는 평균 0.040 m·최대 0.12 m다 — **보이지 않는 4 cm급 단차를 이미
흡수하고 있다.** 턱은 영구 상승·전폭이라 불리하고 조주 구간이 있어 유리하다.
부호를 예측할 수 없으므로 재야 한다. **순서는 `beam`이 먼저다** — 평지 측정만으로
`W_foot`이 나오고 그것이 사다리 값을 정해 주므로 헛돈 사다리를 피한다.

### 액션 차원 개방 커리큘럼 (P2~P3)
설계 문서의 원칙대로 **처음부터 전 차원을 열지 않는다.**

어떤 차원이 어떤 지형을 풀었는지가 그대로 실험 결과물이 된다.

## 부록 B: 명령 범위 근거 재확인 방법

액션 범위를 다시 검토해야 할 때는 아래를 재실행한다. **`scripts/train.py`를 근거로 쓰지 말 것.**

```python
import pickle, io, torch, numpy as np

# 가중치가 CUDA 텐서로 저장되어 있어 CPU 머신에서는 이 패치가 없으면 로드 실패한다
torch.storage._load_from_bytes = lambda b: torch.load(io.BytesIO(b), map_location='cpu',
                                                      weights_only=False)

RUN = "walk-these-ways/runs/gait-conditioned-agility/pretrain-v0/train/025417.456545"

def load_all(p):              # ml_logger는 한 파일에 객체를 계속 append한다 (4983개)
    objs = []
    with open(p, "rb") as f:
        while True:
            try: objs.append(pickle.load(f))
            except EOFError: break
    return objs

# --- 명령 범위: 중첩 경로는 /Cfg/commands (최상위 키는 AC_Args/PPO_Args/RunnerArgs/Cfg) ---
cmds = load_all(f"{RUN}/parameters.pkl")[0]["Cfg"]["commands"]
cmds["gait_duration_cmd_range"]   # [0.5, 0.5]  → duty 상수
cmds["body_roll_range"]           # [-0.0, 0.0] → roll 상수
cmds["binary_phases"]             # True        → gait {0, 0.5} 양자화

# --- 실제 도달 영역: 행=vx, 열=yaw, weights>0 = 학습 도달 ---
dist = load_all(f"{RUN}/curriculum/distribution.pkl")[-1]["distribution"]
M   = dist["weights_trot"].reshape(21, 21)
g   = dist["grid_trot"]
vx  = np.round(g[0].reshape(21, 21)[:, 0], 3)      # bin 중심 (np.linspace 쓰지 말 것)
yaw = np.round(g[2].reshape(21, 21)[0, :], 3)
vx[M.sum(axis=1) > 0].min(), vx[M.sum(axis=1) > 0].max()     # -2.381, 2.381
yaw[M.sum(axis=0) > 0].min(), yaw[M.sum(axis=0) > 0].max()   # -3.333, 2.857
```
**재현 확인 완료 (2026-07-28)**: 위 절차로 duty·roll 폭 0, `binary_phases=True`,
trot vx ±2.381 / yaw [−3.333, +2.857], pronk vx·yaw ±1.905가 모두 재현됨.
- 21×21 격자는 `limit_vel_x`/`limit_vel_yaw` = `[-5, 5]`를 21등분 (중심 간격 0.476).
- vx·yaw 외의 차원은 `num_bins_* = 1` → 커리큘럼 해상도 없음 = 전 구간 균등 샘플.
  그래서 height·footswing·pitch·stance_width는 `parameters.pkl`의 범위를 그대로 신뢰해도 된다.
