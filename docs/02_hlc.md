# 02 · 상위 제어기(HLC) 설계

> **무엇** — 미로를 주행하는 PPO 정책의 설계: 무엇을 보고, 무엇을 내고, 무엇으로 배우나.
> **독자** — HLC를 학습시키거나 고칠 때. 훑어 읽는 설계서다.
> **소유** — 관측·행동·보상·종료·env 파이프라인·PPO 설정.
> 여기 없는 것: 명령 사양은 [01_llc.md §4](01_llc.md),
> 실측 수치는 [03_results.md](03_results.md), 뒤집힌 판단은 [decisions/](decisions/).

환경: Colab + MJX, Unitree Go1. **Sim-only** (실기 이식 없음).
LLC는 WTW `pretrain-v0` **동결**, 8D 연속 명령을 추종한다.

---

## 0. 핵심 설계 결정

| 결정 | 내용 |
|---|---|
| 역할 분리 | **플래너(BFS) = 거시적 방향 지시, PPO = 주행·정밀 정렬, LLC = 보행 실행** |
| 유도 방식 | BFS 거리장의 **기울기 방향(유도 벡터)을 정책 관측으로 직접 제공** (직선 방위 아님) |
| PPO 스코프 | 원안은 **지형 돌파**였으나 실측으로 폐기 → 현재는 **미로 주행**이 본체. [decisions/0001](decisions/0001-지형-돌파-폐기.md) |
| 초기조건 랜덤화 | **소폭 유지(A안)**: 스폰 방위 ±15~20°, 횡 오프셋 ±0.15 m, 조주 거리·초기 속도 랜덤. 목적은 "정렬 기술 학습"이 아니라 **훈련↔배포 분포 일치**(코너 출구의 잔여 오차). 완전 정렬 고정 훈련은 배포 시 분포 이탈로 실패 |
| 경로추종 | 유도 벡터 따라가기는 학습 대상이 아님. 코너·교차로 선택은 전부 플래너 몫 |
| BFS 그리드 | 셀 **0.1 m** 통일 + 쌍선형 보간(보상·유도 벡터의 연속성). **통과 가능성은 지오메트리 래스터화가 아니라 미로 생성기의 의미 정보로 직접 마킹** |
| PPO 입력 | 장애물의 "정답 파라미터"가 아니라 **센서 관측**. 특권 정보를 주면 훈련↔평가 일반화가 성립하지 않는다 |
| LLC 명령 | **8D 연속**, gait는 trot 고정. 지형별 주역 — 터널: height / 틈·턱: footswing / 다리·틈새: stance_width / 경사: pitch |
| 계층 분리 근거 | 성능이 아니라 **학습 예산·검증 용이성·LLC 재사용**을 위한 의식적 선택. 명령 병목(발 위치를 직접 명령 불가)이 성능 상한을 결정 — 극한 지형이 목표면 인지형 단일 정책(관절 레벨)이 연구 표준임을 **인지한 상태의 트레이드오프** |

★ 마지막 항목이 중요하다. 이 근거 셋 중 둘은 LLC를 재학습하는 순간 사라진다 —
그 판단은 [decisions/0004-llc-재학습-보류.md](decisions/0004-llc-재학습-보류.md)에 있다.

## 1. 전체 아키텍처

```
[평가/학습]  미로 생성기 ──▶ BFS 거리장(0.1m, 오프라인) ──▶ 유도 벡터
                                                          ▼
┌─────────────────────────────────────────────────────┐
│                     HLC (10 Hz)                     │
│  [인지] 2D 라이다 16 rays + 유도 벡터                │
│        │                                            │
│        ▼                                            │
│  [내비게이션 정책 (PPO, MLP)]                        │
│        │  raw action (8D 연속)                       │
│        ▼                                            │
│  [명령 필터] 아핀 매핑 · L1 마름모 · 데드존 · 저역필터 │
└──────────────────────┬──────────────────────────────┘
                       │ 8D → 15D 명령 전개
                       │ (gait=trot(0.5,0,0), duty=0.5,
                       │  roll=0.0, stance_length=0.45 고정)
┌──────────────────────▼──────────────────────────────┐
│                LLC (50 Hz, frozen)                  │
│  proprioception + command ──▶ 12개 관절 목표각        │
└──────────────────────┬──────────────────────────────┘
                       ▼
                  MJX 물리 (200 Hz)
```

**주기**: HLC 1스텝 = LLC 5스텝 = 물리 20스텝. `decimation`은 config로.

주의 — 원안에는 **FSM(모드 관리자)** 이 있었다 — 지형 모드 one-hot 제공, 모드별 명령 상·하한
강제, 낙상 감지. 지형 돌파가 폐기되면서 **전환할 지형 모드가 존재하지 않아** `hlc/fsm.py`는
쓰지 않는다. 설계 원형은 [decisions/0001](decisions/0001-지형-돌파-폐기.md)에 남겼다.

## 2. 센서

> **구현 방식: 해석적 질의 우선, `mjx.ray`는 검증용 대체 백엔드.**
> 지형을 우리가 box 파라미터로 생성하므로 광선 추적 없이 동일한 값을 닫힌 형태로
> 계산할 수 있다 (거리 = ray–AABB slab 교차). 이득 셋:
> ① `mjx.ray`의 hfield/mesh 미지원 제약과 무관
> ② 비용이 질의점×box 수의 단순 행렬 연산이라 예측 가능
> ③ **물리와 센서가 같은 파라미터 배열을 읽으므로 불일치가 원천 차단**된다
> (hfield를 물리에 주입하던 방식에서 실제로 겪은 문제).
> 두 백엔드는 동일 시그니처로 구현하고 `mjx.ray` 쪽은 값 일치 테스트에만 쓴다.

| 센서 | 현황 | 사양 |
|---|---|---|
| **2D 라이다** | 사용 중 | 몸통 높이 수평 **16 rays**, FOV 270°(전방 중심), 최대 4 m, `min(d,d_max)/d_max` 정규화 |
| 하향 높이 스캔 | 미구현 | 원안 9×7=63 (초기 7×5=35). 전방 1.2 m × 좌우 0.8 m |
| 상향 클리어런스 | 미구현 | 원안 5점 |
| Proprioception | 완료 | 중력 벡터, 몸통 선속도/각속도, 높이. **관절각은 넣지 않는다** — LLC 소관이고 보행 위상 과적합 위험 |
| 유도 벡터 | 완료 | `(cosφ, sinφ, d_norm)` |

하향·상향 스캔은 **넘을 수 있는 지형이 생기면 그때 만든다.** 지금은 넘을 지형이 없다.

★ **유도 벡터는 훈련·평가가 같은 출력 형식**을 내는 것이 핵심이다 — 형식 통일이 분포
일치를 만든다. `guidance_course`(코스 축)와 `guidance_field`(BFS 쌍선형 보간 기울기)가
같은 3-튜플을 낸다.

## 3. 관측 37D / 행동 8D

```
proj_gravity(3) + 월드 선속도(3) + 각속도(3) + 몸통 높이 AGL(1)
+ 유도 벡터(3) + 직전 명령(8) + 라이다(16)                     = 37
```

원안은 라이다 32 + 높이스캔 63 + 클리어런스 5 + 모드 one-hot 7을 더해 ~130D였다.
지형 돌파 폐기로 **21D → 37D**가 됐다(77D가 아니라).

★ **관측에 절대좌표도 맵 크기도 없다.** 따라서 정책은 원리적으로 크기·배치에
무관해야 한다 — 다만 그것은 **가설이지 결과가 아니고**, P5가 그것을 판정한다.

주의 — 유일한 예외가 `d_norm`이다. 관측 중 홀로 `_course_len`으로 정규화되므로 코스 길이에
따라 변화율이 달라진다. **큰 미로에서 성능이 떨어지면 여기를 먼저 의심할 것.**

조립은 `nav_env._obs`.

**행동 8D** (tanh → 아핀 매핑): `vx, yaw_v(= v_yaw), vy, height, step_freq, footswing,
pitch, stance_width`.
범위와 고정 차원은 [01_llc.md §4.5](01_llc.md)가 소유한다.

**네트워크**: MLP 3층 (512-256-128), tanh 가우시안. Critic 동일 구조 별도.
순환 구조는 부분관측 문제가 확인될 때만 도입.

## 4. 보상 / 종료

```python
r = 10.0  * (d_prev - d_now)       # progress (유도 방향 투영 거리), potential-based
  + 100.0 * reached                # 도달 보너스
  - 0.05                           # 시간 페널티
  - 5.0   * terminated_bad         # 전복/추락/교착
  - 0.01  * ||cmd_t - cmd_{t-1}||²  # 명령 급변
  - 1.0   * body_contact           # 몸통/허벅지 접촉

done: 완주 | 전복(proj_grav_z > -0.5) | 추락(z < z_floor - 0.3)
타임아웃: done에 넣지 않는다 (§5.2)
```

★ **핵심 메커니즘**: 돌파 기술은 `progress(건너려는 동기) × 추락 종료(어설픈 시도의 대가)`
에서 나온다. 위험 지형에 **별도 성형 보상을 주지 않는다** — BFS/유도는 "어디로"만 알고
"떨어지면 안 됨"은 종료 조건이 가르친다.

주의 — `reach`가 10이 아니라 **100**, `time`이 −0.01이 아니라 **−0.05**인 데에는 실패
기록이 있다(§5.3).

## 5. env 파이프라인과 학습 설정 — 조용히 실패하는 것들

### 5.1 JAX 제약 — `reset`은 `jit`/`vmap` 안에서 돌아야 한다

`reset()` 안에서 `mujoco.MjData(...)` / `mjx.put_data(...)`를 부르면 **Python 부수효과라
`jit`/`vmap` 안에서 동작하지 않는다.** 2048 env 병렬 리셋이 불가능해진다.

```python
# __init__
self._init_data = mjx.put_data(self.mj_model, mj_data)   # 1회
# reset
data = self._init_data.replace(qpos=qpos, qvel=qvel)
data = mjx.forward(self.mjx_model, data)                  # kinematics만으로는 부족
```
`mjx.kinematics`가 아니라 **`mjx.forward`** 를 써야 첫 관측의 접촉/센서 값이 유효하다.

### 5.2 ★ 타임아웃을 `done`에 넣지 말 것 (brax truncation)

한 실행이 **도달률 15.6%까지 갔다가** 무너졌다. 붕괴 시작점이 `len`이 상한 300에 닿은
직후와 정확히 일치했다. brax 0.14.1 `EpisodeWrapper.step`:

```python
state.info['truncation'] = jp.where(steps >= episode_length, 1 - state.done, zero)
```

env가 같은 스텝에 `done=1`을 세우면 `truncation = 0`이 되어 brax가 시간 초과를 **진짜
종료로 오인**하고 가치 부트스트랩을 0으로 자른다. "17 m 걸어왔고 아직 걷는 중"인 상태의
가치가 0이 되니, 오래 걷는 정책일수록 손해를 보고 학습이 짧은 에피소드로 붕괴한다.
시간 제한은 `train.py`가 `episode_length`로 넘겨 EpisodeWrapper가 처리하게 둔다.

**부수 효과**: `done`에서 타임아웃을 빼면 `dist * done` 지표가 시간 초과 에피소드에서
0이 된다. 지표 전용 `last`(타임아웃 포함) 플래그를 따로 쓸 것.

수정 후 붕괴가 사라졌다 — 6.5M 스텝 동안 `len≈300`, `dist` 1.2~6.4로 안정.
게이트 `test_nav_env` [11]이 이 불변식을 고정한다.

### 5.3 ★ 보상 유인의 **상대 크기**를 학습 전에 볼 것

다른 실행은 붕괴하지 않았지만 **도달률이 0.17에서 6.5M 스텝 동안 오르지 않았다.**
원인은 학습이 아니라 설계였다:

```
총 progress 보상 = 10 × (19.62 − 1.24) = 183.8
관측된 리턴      = 184.6      ← 리턴이 전부 progress
```

| 항목 | 리턴 대비 |
|---|---|
| 마지막 1.24 m를 마저 가서 도달 (+12.4 +10) | **11%** |
| 300스텝 시간 페널티 전체 (−3) | 1.6% |
| 100스텝 빨리 끝내기 (+1) | **0.5%** |

정책은 이미 얻을 수 있는 리턴의 97%를 확보했다. **마무리할 이유도 서두를 이유도 없었고**,
실제로 18.4 m를 30초에 걸쳐 0.61 m/s로 느긋하게 갔다(LLC는 vx=0.8에서 0.86 m/s를 낸다).
정책은 보상대로 행동했다.

수정: `reach` 10 → **100**, `time` −0.01 → **−0.05**. 마무리 유인 7% → **37%**.

**`python -m wtw_nav.envs.reward_audit`** 가 이 부류를 학습 전에 잡는다(JAX 불필요, 몇 초).
대표 시나리오의 리턴을 나열하고 ① 도달 vs 거의 도달 격차 ② 속도 유인 ③ 순위 역전을
검사한다. 옛 상수를 넣으면 ①이 7%로 FAIL 난다. **보상 상수를 건드릴 때마다 돌릴 것.**

### 5.4 주의 — PPO 하이퍼파라미터 — 조용히 실패하는 넷

첫 P1 학습이 실패했다. 정점(655k 스텝, reward 46.3, dist 14.7 = 5 m 전진) 뒤 **단조 하강**해
끝에는 `len=30`(교착 최소 창), `dist=20.1`로 아예 안 움직였다. `fell=0`이었으므로
물리·env 문제가 아니라 **학습 설정 문제**다.

**(가) 갱신 횟수가 실제 학습량이다.** brax는 `batch_size × unroll_length × num_minibatches`
만큼의 env 스텝을 모아야 정책을 **한 번** 갱신한다. 1024×20×32 = 655,360이면 예산 10M에서
갱신이 15회뿐이다. 로그에서 행 간격이 곧 이 값이므로 눈으로 확인할 수 있다.
**수백 회가 필요하다.**

**(나) `num_evals`가 `num_timesteps`를 덮어쓴다.** eval마다 최소 1회 학습하므로 실제 스텝
≥ `num_evals × env_step_per_training_step`. 40 × 655,360 = 26.2M이라 10M을 지정했는데
25.5M을 돌았다. **eval 비용도 크다 — 101분 중 18분.**

**(다) 엔트로피 항이 정책 손실을 압도할 수 있다.**

```
training/policy_loss          = -0.00025
training/entropy_loss         = -0.05361      ← 200배
training/policy_dist_mean_std =  0.798        ← 끝까지 최대치 근처
```

`entropy_cost=1e-2`가 우리 보상 규모에 비해 컸다. 옵티마이저가 리턴이 아니라 엔트로피를
최대화하니 정책이 수렴하지 못하고 성능이 하강한다. **`policy_loss`와 `entropy_loss`의
비를 반드시 볼 것** — 이 둘이 같은 자릿수여야 한다.

**(라) 할인율은 에피소드 길이를 덮어야 한다.** γ=0.99는 유효 지평 100스텝(10 s)인데
코스 주파는 20~30 s다. 가치함수가 목표를 보지 못한다. γ=0.997 → 지평 333스텝.

수정 결과 갱신 39회 → **183회**. `train._check_ppo_config()`가 (가)(나)를 학습 시작 전에
경고한다.

주의 — **`num_timesteps`는 반올림된다.** brax는 `(num_evals-1) × batch × unroll × minibatches`의
배수로 올림하므로 6,000,000을 넣으면 6,881,280(+14.7%)을 돈다.
`configs.maze_config()`가 정확한 배수를 계산해 낭비를 없앤다.

### 5.5 주의 — brax 래퍼와 `lax.scan` 캐리 구조

brax PPO는 env state를 `lax.scan` 캐리로 쓴다. **`reset`과 `step`이 내는 `metrics`/`info`의
pytree 구조가 다르면** 다음으로 죽는다:

```
TypeError: scan body function carry input and carry output must have the same
pytree structure ... state.metrics is a dict with 5 children but ... 4 children,
symmetric difference of key sets: {'reward'}
```

원인: `step`에서 `metrics`를 **새 dict로 교체**하면 brax `EvalWrapper`가 끼워 넣은
`metrics['reward']` 키가 사라진다.

```python
metrics = dict(state.metrics)          # ← 교체하지 말고
metrics.update(progress=..., fell=...) #    갱신할 것
```

`info`도 같다 — `dict(state.info)`로 복사한 뒤 갱신해야 `EpisodeWrapper`의 `steps`·
`truncation`, `AutoResetWrapper`의 `first_pipeline_state`가 살아남는다.
`test_nav_env.py` [10]이 `brax_training.wrap()`과 `EvalWrapper`를 씌워 이 구조를 검사한다.

### 5.6 지형 랜덤화 = `randomization_fn`

병렬 env마다 지형이 달라야 하는데 지형은 `mjx_model.geom_pos/geom_size`에 있다.
Brax PPO는 이를 위해 `ppo.train(randomization_fn=...)` 훅을 제공한다.

```python
def domain_randomize(mjx_model, rng) -> (batched_model, in_axes)
#   geom_pos / geom_size 를 배치 축 있게, 나머지는 in_axes=None
```

**제약: geom 개수는 전 env 고정.** 따라서 코스는 "슬롯 M개 × 슬롯당 box 최대 B개"로
고정 배열을 만들고, 사용하지 않는 box는 지면 아래로 치워 무력화한다(`pos.z = -10`).
지형 종류 변경 = 파라미터 변경일 뿐 **재컴파일 없음**.
같은 파라미터 배열을 센서에도 그대로 넘겨 **물리와 센서가 항상 일치**하게 만든다.

## 6. 학습 전 검증 — 세 단계, 이 순서로

뒤로 갈수록 비싸므로 순서가 중요하다.

| 단계 | 명령 | 잡는 것 |
|---|---|---|
| 1 | `python -m wtw_nav.llc.test_policy` | LLC 상수·관측 조립·DOF 순서 (JAX 불필요) |
| 2 | `python -m wtw_nav.envs.test_nav_env` | **vmap 가능성**, brax 래퍼 pytree 구조, 차원·유한성 |
| 3 | `python -m wtw_nav.envs.scripted` | **env가 풀 수 있는 문제인가** + 타임아웃 여유 |

★ **3단계가 특히 중요하다.** 유도 벡터만 보는 단순 비례 제어기가 목표에 못 가면 성능이
아니라 **보상·종료·유도벡터가 틀린 것**이고, 그 사실을 30M 스텝 태운 뒤에 알아내는 것은
낭비다. P4가 한 번에 성공한 직접적 이유가 이 게이트다([03_results.md §5](03_results.md)).

> **타임아웃 여유 (실측으로 잡은 문제)**: 기준 제어기(vx 1.0)가 20 m 코스를 **19.1 s**에
> 주파했는데 타임아웃이 20 s였다. 여유가 0.9 s뿐이면 **기준보다 조금만 느린 정책은 전부
> 타임아웃되어 도달 보너스를 한 번도 못 받는다** — 학습이 엉뚱한 이유로 실패한다.
> → `timeout_s`를 30 s로 올렸다. 정책은 vx를 1.9까지 낼 수 있어 **원리상 10.5 s면 간다.**
> `scripted.py`가 이제 여유를 자동 계산해 30% 미만이면 경고한다.

그리고 학습 **비용**은 `python -m wtw_nav.bench`로 먼저 잰다. 주의 — raw `env.step` 수치를
그대로 믿지 말 것 — PPO 갱신과 eval이 얹혀 실측 계수가 **×0.58**이다([03_results.md §5.2](03_results.md)).

## 7. 미로 생성과 BFS 거리장

- 셀 기반 미로, **통로 폭 2 m**. `terrain/maze.py`의 `generate(n, seed, loop_prob)`.
- ★ **벽은 직선 구간마다 박스 하나로 병합한다** (5×5에서 33 → **13 geom**).
  단일 메시로 만들 수 없는 이유: **MuJoCo 프리미티브는 볼록**이라, 미로 벽 네트워크를
  메시 하나로 두면 **볼록 껍질로 충돌**해 통로가 막힌다. 병합은 검증했다 — 단일 슬롯
  구간은 옛 공식과 동일하고, 병합 구간은 개별 구간의 합집합(랜덤 300회), 외곽은 항상 4개.
- **BFS 거리장**: 셀 **0.1 m** 통일. 16 m × 16 m 미로 = 160×160셀, numpy 밀리초 수준 —
  해상도에 상한 압력이 없다. 읽기는 항상 쌍선형 보간 → 유도 벡터·거리값이 연속.
- **통과 가능성은 생성기 의미 정보로 직접 마킹** (래스터화·인플레이션 추정 금지):
  - 일반 벽: 안전 마진 포함 통과 불가
  - 의도된 좁은 틈새: 인플레이션 없이 통과 가능 — 표준 인플레이션은 몸 폭 수준의
    틈을 막아버리므로
  - 낙차·다리 옆 허공: 통과 불가
- **위험 지형 셀의 비용은 균일하게.** 우회 선호를 심으면 돌파 학습 기회가 사라진다.

`configs.maze_config(n, seed, cruise, corner_slack)`이 미로 크기에서 타임아웃·에피소드
길이·`num_timesteps`를 역산한다 (BFS 홉 수 × PITCH = 경로 길이 → `cruise` 속도 →
`corner_slack` 배수).

**폐기된 커리큘럼** (지형 돌파 전제였음, 이력으로만 남김):
```
stage A: 4D (vx, vy, yaw, height)   ← 전 지형 우선 시도
stage B: + footswing        (틈/턱 실패 시)
stage C: + stance_width     (다리/틈새 실패 시)
stage D: + pitch            (경사 실패 시)
stage E: + gait(이산) + step_freq  ← vx/yaw 상한을 pronk 마름모 1.4/1.4로 축소
```
원칙은 "처음부터 전 차원을 열지 않는다 — 어떤 차원이 어떤 지형을 풀었는지가 그대로
실험 결과물이 된다"였다. 지형이 사라지면서 근거도 사라졌고, 현재는 8D를 한 번에 연다.
