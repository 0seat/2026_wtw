# 03 · 실측 대장

> **무엇** — 이 프로젝트가 **실제로 측정한 것**과 그 값이 나온 경위.
> **독자** — "그 숫자 어디서 나왔지", "이건 이미 해봤나"를 확인할 때.
> **소유** — 측정 수치와 경위. 설정 방법은 [01_llc.md](01_llc.md), 설계는 [02_hlc.md](02_hlc.md).

**이 문서는 덧붙이기만 한다.** 결과는 뒤집히지 않는다 — 해석이 뒤집히면
[decisions/](decisions/)에 기록하고 여기에는 반증 사실을 덧붙인다.

★ **측정 원칙**: PPO 이전에 **고정 명령 대조군**부터 잰다. 대조군이 곧 하한이고, PPO는
그 위를 얼마나 올리는지로만 평가한다. 지형 한계 **값 자체의 소유자는
`wtw_nav/terrain/limits.py`** 이고 여기는 그 값이 나온 경위를 남긴다.

## 1. LLC 이식 (P0) — 2026-07-28

### 1.1 원인은 DOF 순서 하나였다

증상·원인·근거는 [01_llc.md §3](01_llc.md).
수정 후 18개 명령 × 5 s 검증:

| 명령 | min_z | 측정 |
|---|---|---|
| vx=+0.8 | 0.149 | **vx = 0.854** ← P0 기준 0.6~0.9 |
| vx=+1.2 | 0.128 | vx = 1.192 |
| vx=−0.5 | 0.176 | vx = −0.430 |
| vy=+0.4 | 0.177 | vy = 0.484 |
| yaw=+0.8 | 0.165 | wz = 1.042 |
| pronk, freq=2.0 | 0.121 | 4足 체공 24% |
| pronk, freq=3.9 | 0.165 | 4足 체공 26% |

`|a|max`가 10.00(포화) → **4.3~5.4**로 내려갔고 낙상이 사라졌다.
height/footswing/stance_width/pitch/bound/pace도 모두 정상.
최종 MJX(GPU): `vx=0.8 → 0.871`, `vy=0.4 → 0.480`, `yaw=0.8 → 1.058`, `min_z=0.155`.

로컬 정적 게이트 25/25 → 이후 29/29 PASS (MLP forward vs torch `max|diff| = 9.2e-05`).

> 주의 — 위 표의 "pronk 체공 24~26%"를 한때 **"점프 가능"으로 판정했으나 틀렸다.**
> 체공률은 점프의 증거가 아니다 — 다리를 몸쪽으로 접기만 해도 발은 뜬다. §2 참조.

### 1.2 배제된 가설 — 재검증 불필요

전부 실측으로 확인했고 **어느 것도 원인이 아니었다.**

| 가설 | 결과 |
|---|---|
| actuator_net ↔ PD 격차 | 유효 Kp = **18.7~20.1** (우리 PD Kp=20과 동일), 유효 Kd = 0.75~0.85 |
| PD 게인 부족 | Kp 20/40/60/100 전부 붕괴 |
| 토크 한계 | URDF effort **33.5** vs menagerie **23.7** 불일치를 발견·수정했으나 결과 불변. 무제한 토크에서도 붕괴 |
| `ctrl` 클램프 (ctrlrange) | 불변 |
| 관절 damping / frictionloss / armature | 불변 |
| 접촉 모델 (cone/impratio/condim/solimp/solref) | menagerie 원본으로 되돌려도 붕괴 |
| solver iterations (**MuJoCo C 엔진**) | 1~100 전부 동일 (단 `implicitfast`+iters=1은 발산). 주의 — **MJX는 다르다 — §1.3** |
| 마찰 계수 0.3 / 0.8 / 1.0 | 불변 |
| 질량 (URDF 11.31 kg vs menagerie 12.74 kg) | URDF 값으로 스케일해도 붕괴 |
| 중력 10%~100% | 전부 붕괴 → 힘 부족이 아님 |
| 초기 충격 (0.5/1.0 s 정착 후 시작) | 불변 |
| 행동 지연 `lag_buffer` 0~40 ms | 불변 |
| 히스토리 순서 (최신 앞/뒤) | 양쪽 다 붕괴 |
| 관측 정규화 | `ac_weights_last.pt`에 running mean/var 없음 → 원시 관측이 맞음 |

> **교훈 ①** — 중력을 10배 바꿔도 `min_z`가 0.055~0.059로 거의 동일했다. **물리
> 파라미터가 결과를 지배하지 않는다는 것 자체가** "물리가 아니라 정책 되먹임이
> 원인"이라는 신호였다. 이 신호를 더 빨리 읽었다면 플랜트 스윕을 건너뛸 수 있었다.

> **교훈 ②** — 합성 관측 프로브(정지 직립 30프레임)는 관측 **레이아웃**은 검증했지만
> 30프레임을 동일 값으로 채웠기 때문에 **다리 대응·시간축 구조**를 검증하지 못했다.
> 이런 축은 추론보다 **폐루프 전수 조사**가 빠르고 확실하다.

### 1.3 MJX는 solver 반복이 더 필요하다 — 미수렴 해는 하드웨어 의존적

관절 순서를 고친 뒤에도 **Colab(MJX)에서만** 다시 무너졌다. 로컬 MuJoCo C 엔진에서는
잘 걸었다.

```
             vx=+0.8            vy=+0.4            vx=-0.5
 4/8    0.218  min_z 0.058 낙상   -0.034  낙상      -0.564  정상
 8/16   0.777  min_z 0.155 정상    0.440  정상      -0.430  정상
16/32   0.777  min_z 0.155 정상    0.439  정상      -0.430  정상   ← 8/16과 동일 = 수렴
MuJoCo C (iters 4)  0.865                0.490      -0.432
```

같은 코드·같은 설정을 **로컬 MJX(CPU)** 에서도 돌려봤더니 결과가 갈렸다:

| | 4/8 | 8~10/16~20 |
|---|---|---|
| MJX **CPU** (로컬) | vx **+0.859**, min_z 0.172, 정상 | vx +0.776, min_z 0.155, vy +0.370 |
| MJX **GPU** (Colab) | vx **+0.218**, min_z 0.058, **낙상** | vx +0.777, min_z 0.155, vy +0.370 |

**4/8에서는 CPU와 GPU가 완전히 다른 결과를 낸다.** 반면 반복을 충분히 올리면 두 백엔드가
소수점 3자리까지 일치한다. 미수렴 구간에서는 부동소수점 차이가 접촉 해를 갈라놓고 그
차이가 폐루프에서 증폭된다(로컬 4/8의 `vy=-0.236`이 10/20에서 `+0.370`으로 **부호까지**
뒤집힘).

→ 기본값 **`iterations=8, ls_iterations=16`** 확정. 16/32가 동일하므로 더 올릴 이유가 없다.

> 주의 — **교훈**: MuJoCo C 엔진 결과나 정적 유지 테스트로 MJX의 solver 설정을 정하면 안 된다.
> C 엔진은 iterations=4에서도 멀쩡히 걷고 **MJX CPU조차 4/8에서 통과해 버린다** — 그래서
> "4면 충분하다"는 잘못된 확신을 준다. 이 문서가 한때 "solver iterations 1~100 전부
> 안정적"이라고 적었던 것이 바로 그 함정이었다.
> **판정 기준은 "돌아가느냐"가 아니라 "반복을 늘려도 결과가 변하지 않느냐(수렴)"다.**

### 1.4 정지 시 +0.09 m/s 전진 편향 — 잔여 특성

`vx=0` 명령에서도 로봇이 지속 전진한다. 초기 착지 과도현상이 아니다:

```
1~5 s 구간 0.0948 m/s   5~10 s 구간 0.0930 m/s   (완벽히 선형)
MJX(GPU) 0.088 · MuJoCo C 0.093  → 엔진 무관 = 이식 오류가 아님
```

원인을 좁히려 조정해봤으나 **모두 추종 성능을 악화시켰다**:

| 설정 | 정지 편향 | vx=0.8 추종 |
|---|---|---|
| **현재 (menagerie 12.74 kg, Kd=0.5)** | **+0.095** | **0.800** ← 거의 완벽 |
| 질량 URDF 맞춤 (11.31 kg) | +0.124 (악화) | 0.908 (과추종) |
| Kd=0.8 (actuator_net 유효값) | +0.080 | 0.743 (미달) |
| 둘 다 | +0.100 | 0.791 |

→ **현재 설정 유지.** 편향은 sim-to-sim 격차(actuator_net→PD 근사)의 잔여물로 보이며,
명령 범위(0.5~1.9 m/s) 대비 작다. HLC가 폐루프로 보정하므로 문제되지 않지만
**"정지"를 명령해도 천천히 전진한다.**

## 2. 도약 탐색 — 불가 확정

`duty`가 0.5로 고정 학습된 탓에 점프 가능성이 설계 최대 리스크였다.

### 2.1 초기 관측 (pronk 정상상태) — 체공률은 점프의 증거가 아니다

MuJoCo C, solver 8/16, 0.5 s 이후:

| 명령 | 체공률 | 지속 | **정점 상승** | **체공 중 수평이동** | 몸통 z 진폭 |
|---|---|---|---|---|---|
| pronk vx=0.3, f=2.0 | 23.3% | 116 ms | **+0.001 m** | +0.024 m | 0.233 |
| pronk vx=0.8, f=2.0 | 21.1% | 105 ms | **+0.000 m** | +0.052 m | 0.243 |
| pronk vx=1.2, f=2.0 | 22.5% | 113 ms | **+0.001 m** | +0.089 m | 0.224 |
| pronk vx=1.2, f=2.5 | 30.5% | 120 ms | **+0.002 m** | **+0.106 m** | 0.152 |
| trot vx=1.2 (참조) | 0.0% | — | — | — | 0.076 |

**정점 상승이 사실상 0이다 — 몸통이 뜨지 않는다.** 발이 떨어지는 것은 다리를 접기 때문이며
몸통은 오히려 깊게 내려앉는다(z 진폭 0.22 vs 트롯 0.076). 앞/뒤 접지율도 비대칭이다(0.71 vs 0.61).

**MJX에서는 아예 전복된다:**
```
MJX   pronk vx=0.3 f=2.0 :  fell=True   pg_z 평균 +0.878   z 평균 0.101
MJX   trot  vx=0.8       :  fell=False  pg_z 평균 -0.999   z 평균 0.251
```
`pg_z = +0.878`은 중력이 몸통 기준 +z를 향한다는 뜻 — **로봇이 뒤집혀 누워 있다.**
MuJoCo C 엔진은 직립을 유지하며 어설프게 튀는 데 그치지만 MJX에서는 전복된다
(§1.3과 같은 계열의 엔진 불일치. **결론은 양쪽 모두 "점프 아님"으로 동일**).

> **지표 수정의 필요성**: 뒤집힌 로봇의 발은 당연히 공중에 있다. 느슨한 지표
> (`min 발 클리어런스 > 0.03`)로는 MJX의 전복 상태가 **17.3% "체공"** 으로 집계된다.
> 직립·높이 조건을 넣은 `jump_metrics()`는 0%로 올바르게 판정한다.

### 2.2 체계적 탐색 (72개 조합) — 전부 실패

`gait{pronk,bound,pace} × freq{2.0,2.7,3.4} × footswing{0.20,0.35} × height{-0.20,0,+0.13}`
정상상태 60개 + 과도(웅크림→펴기) 프로토콜 12개. 모두 vx 0.6/1.2.

```
체공 중 수평이동 최대   +0.082 m   (pronk f=2.7 fs=0.35 h=+0.13)
bound  전 조합          ≈ 0.000 m  (4발 동시 체공이 거의 없음)
pace   전 조합          ≈ 0.000 m
과도 프로토콜 12종      최대 +0.057 m  (정상상태보다 나쁨)
```

`zmax`가 거의 모든 조합에서 **0.337 = 초기 스폰 높이**다. 몸통이 그 위로 올라간 적이 없다.

**토크 한계가 아니다.** 5 cm 도약에 필요한 관절 토크는 다리당 약 9 Nm로 한계
(23.7~35.55 Nm) 안이다. 물리적으로 불가능한 게 아니라 **정책이 시도하지 않는다.**

★ 이 탐색은 초기 판정이 **근거 부족**이었기 때문에 열린 것이다. 처음에는
`pronk × vx{0.3,0.8,1.2} × freq{2.0,2.5} × footswing{0.32,0.35}` — 정상상태 명령 4~5개만
보고 결론을 냈고, `height` 과도 조작(웅크림→펴기)과 `bound` gait를 전혀 탐색하지 않았다.
그 셋을 채운 결과가 위 표다.

### 2.3 왜 시도하지 않는가 — WTW의 도약 기능은 **구현되지 않았다**

체크포인트 config에 `impulse_height_commands: False`, `jump_interval_s: 20.0`,
`jump_duration_s: 0.1`, `jump_height: 0.3`이 있어 "끄고 학습했다"로 보였으나,
**소스를 뒤져보면 이 네 값은 어디에서도 읽히지 않는다** — 죽은 설정 필드다.

```
grep -rn "impulse_height_commands|jump_interval|jump_duration|jump_height" --include=*.py .
  -> legged_robot_config.py 의 선언 4줄뿐. 사용처 0.
```

`reward_scales.jump = 10.0`은 실제로 쓰이지만, `_reward_jump`(`corl_rewards.py:60-64`)는
`commands[:,3] + base_height_target` 추종 보상 — **이름만 jump이고 실제로는 몸통 높이
추종**이다. 즉 WTW 공개 코드에는 **도약 메커니즘 자체가 없다.** 우리가 이미 height를
전 범위로 쓸어본 것이 이 메커니즘의 전부였다.

→ **config 플래그를 켜는 것으로는 도약을 얻을 수 없다. 코드를 새로 써야 한다.**

## 3. 지형 실측 6종 (2026-08-06 ~ 08-09)

공통 장치: `terrain/modules.ladder()`(난이도를 코스 x축에 배열) +
`envs/scripted.evaluate()`(시드별 `level` = 넘긴 장애물 수) + **매 실험 영상**.

| 지형 | **원안**(측정 전 희망) | **실측** | 설계값(여유) | 시드 | 상태 |
|---|---|---|---|---|---|
| `gap` | 0.1~0.7 m | **0.05 m** | 0.035 (×0.7) | PPO 6.9M + 대조군 | 확정. **원안 상단의 7%** |
| `slope` | ±10~25° | **20°** | 14 (×0.7) | 3 | 확정. 원안 범위 안 |
| `tunnel` | 0.2~0.35 m | **0.291 m** | 0.335 (×1.15, **하한임에 주의**) | 3 | 확정. 원안 범위 안 |
| `rough` | (원안 없음) | **±0.06 m (진폭)** | 0.042 (×0.7). 평균 단차 2a/3 = 0.040 | 5 | 신설·확정 |
| `ledge`(턱) | 0.05~0.25 m | **0.07 m** | 0.049 (×0.7) | 위상 8 | 확정 |
| `beam` | 0.1~0.3 m | 기하 0.321 / 벽 0.55 | — | 3+5 | ★ **제외** (§3.5) |
| `slit` | ≈ 로봇 폭 | — | — | — | 영구 제외 |
| `jump` | — | 정점 상승 +0.001 m | — | 72조합 | 영구 제외 |

주의 — **원안 열은 설계 시점의 희망이며 측정된 적이 없었다.** `gap`이 상단의 7%로 나온 것이
[0001](decisions/0001-지형-돌파-폐기.md)의 직접 계기다. 원리적으로 불가능한 과제를
커리큘럼에 두면 정책은 영원히 실패하고 우리는 그것을 "학습이 덜 됐다"로 오진한다 —
P1에서 도달 불가능한 코스(20 m/30 s)에 6.5M 스텝을 태운 것이 정확히 그 사고였다.
그래서 `limits.validate()`는 **미측정 지형을 조용히 잘라내지 않고 거부한다.**

★ **2026-08-09로 6종 실측이 전부 끝났다** — `limits.report()`가 처음으로
"전 지형 실측 완료"를 찍는다.

★★ **여섯 지형 전부에서 낙상이 0건이다.** 한계를 정한 것은 매번 전복이 아니라
**추진 정지(slope) · 명령 포화(tunnel) · 해가 명령 공간에 없음(gap)** 이었다.
설계에 그대로 쓰인다 — 미로에서 위험한 것은 "넘다가 넘어짐"이 아니라
**"넘지 못하고 갇힘"** 이므로, 종료 조건은 낙상이 아니라 **교착**을 잡아야 한다.

### 3.1 경사 20° — ★ 가설이 반증됐다

1차 측정에서 24°에 막혔는데 그때 로봇이 **−126° 회전하고 y로 −1.55 m 표류**해 있었다.
"지형이 아니라 내 제어기가 만든 한계"라는 유보를 달아 뒀다. `guidance.heading_hold`와
같은 법칙을 `scripted.guidance_controller`에 넣고(`hold=1`) A/B로 다시 쟀다:

| | level(pitch 0.0) | level(pitch 0.3) | 종료 yaw | 종료 y | 최대 x |
|---|---|---|---|---|---|
| `hold=0` | 2.00 | **3.00** | −126° | −1.55 | 12.39 |
| `hold=1` | 2.00 | **3.00** | **−0°** | **−0.07** | 12.43 |

진로 유지기는 완벽히 작동했다(회전·표류가 사라짐). **그런데 level이 같다.**
→ **회전은 원인이 아니라 결과였다.** 램프에서 먼저 막히고 그 다음 돌아선 것이다.
20°를 확정하고 유보를 뗐다. **같은 논리로 `gap` 0.05의 유보도 철회.**

참고로 마찰 상한은 `atan(0.6) = 30.96°`이고, WTW 학습 시 중력 랜덤화
(`gravity_range=[-2,2]`)의 실효 기울기가 평균 8.97° / p90 13.3°다.
실측 20°는 **학습 분포의 p90보다 위** — 경사는 학습된 강건성이 잘 외삽된 경우다.

### 3.2 터널 0.291 m — ★ 평지 예측이 실지형에서 정확히 맞았다

지형을 만들기 전에 **평지에서** `scripted.body_clearance()`로 명령별 로봇 최고점을 쟀다.
그 값으로 사다리 결과를 예측하고, 그 다음 실지형을 돌렸다:

| height 명령 | 평지 최고점 | 예측 level | **실측 level** |
|---|---|---|---|
| −0.22 | 0.291 m | 5 | **5.00** ✓ |
| 0.00 | 0.337 m | 4 | **4.00** ✓ |

주의 — `_geom_top`은 **회전을 반영한 형상별 z반경**을 쓴다. `geom_rbound`를 쓰면 몸통 박스가
반경 0.20으로 잡혀 실제 윗면(중심+0.057)의 3.5배가 되고 예측이 통째로 틀린다.
이 예측 적중은 그 구현이 맞았다는 증거다.

주의 — **두 개의 수가 있다.** `height=-0.08`(최고점 0.320 > 천장 0.30)도 level 5를 냈다 —
천장에 **닿고도 비벼서 밀고 나갔다**. 설계에는 **접촉이 없는 0.291**을 쓴다.

★ 이 "평지에서 재고 → 예측하고 → 실지형으로 확인" 절차는 `beam`에 그대로 재사용했다.

### 3.3 요철 진폭 0.06 m — 세 번 고쳐서야 유효한 측정이 됐다

`_rough_patch`: 중앙 띠(반폭 1.0 m)에 `nx × 6` 격자 박스, 윗면 z를 U(−a,a)로 흔든다.
양옆은 평평한 슬래브(표류해도 낙하하지 않도록).

**세 번 다 "실패가 성공처럼 보이는" 종류였다:**

1. **레인 3개(홀수) → 롤 교란 0.** 가운데 레인이 y=0에 걸터앉고 그 폭 0.667 m가
   `stance_width` 최대 0.42 m보다 넓어 **좌우 발이 항상 같은 타일**을 밟았다.
   짝수(6)로 바꿔 레인 경계를 정확히 y=0에 놓았다. `ValueError` 가드를 넣었다.
2. **첫 사다리(0.02~0.07)가 너무 쉬웠다** — level 5.33, 여러 축이 6.00(완주)으로 천장을
   쳤다. 원인은 "단차 = 2×진폭"이 **최악값**이었다는 것. 이웃 타일이 독립 U(−a,a)면
   단차는 삼각분포라 **평균 |Δ| = 2a/3**이고 `P(|Δ|>d) = (1−d/2a)²`다. a=0.07의 평균
   단차는 0.047 m로 gap 실측 0.05와 같은 자릿수 — 통과가 당연했다. 평균 단차 기준
   등간격으로 재설계: `(0.06 … 0.21)`.
3. **띠를 벗어나 옆 평지를 밟았다** (영상에서 확인, y가 한 방향으로만 +0.12→+0.70).
   LLC의 요속 편향 ω≈0.118 rad/s가 **계통적**이라 매번 같은 쪽으로 샜다.
   → ★ **띠를 넓히지 않고 제어기를 고쳤다.** 넓히는 것은 geom을 2배로 늘리면서
   원인(되먹임 부재)은 그대로 두는 증상 대처이고, 표류가 시간에 2차로 자라므로 어떤
   폭도 충분하지 않다. `hold=1` + **이탈 비율을 매 실행 계측**(`scripted._report_off_band`).

최종: n=5, `hold=1` → **level 1.40** (2,2,1,1,1). **0.06은 5/5, 0.09는 2/5** 통과.
띠 이탈 1%, |y|max 1.10 — 오염 없음. `rough_report()`가 단별 타일 72개와 윗면 z 폭
0.119~0.419(= 2×진폭)를 모델에서 직접 읽어 확인했다.
`hold=0`도 1.33으로 거의 같다 — **요철에서는 표류가 실패 원인이 아니었다.**

★ 오염된 1차 사다리와 **모순되지 않는다**: 둘 다 벽이 a=0.07과 0.09 사이임을 가리킨다.
독립적인 두 사다리가 같은 곳을 짚었다.

주의 — **`rough` 평균 단차(0.040)와 `gap`(0.05)을 같은 척도로 비교하지 말 것.**
틈은 지면이 없어 발이 빠지고, 요철은 지면이 있어 다리 PD가 흡수한다.

### 3.4 턱 0.07 m — ★ "LLC로는 턱을 못 넘는다"가 반증됐다

`scripted.phase_sweep`, 위상 8점 × 시드 1. 사다리 `(0.03, 0.05, 0.07, 0.10, 0.13, 0.17)` 증분.

| 증분 | 누적 | 도달 | 조건부 성공률 |
|---|---|---|---|
| 0.03 / 0.05 / **0.07** | 0.03 / 0.08 / 0.15 | 8 | **100%** |
| 0.10 | 0.25 | 8 | 75% |
| 0.13 | 0.38 | 6 | 33% |
| 0.17 | 0.55 | 2 | 0% |

**0.07 m는 8/8이다.** 사전 예측 구간(0.05~0.10)이 맞았고,
`gap 0.05 < ledge 0.07 < rough 최대단차 0.12` 순서도 물리적으로 일관된다 — 지면이 있으니
틈보다 낫고, 요철은 오르내림이 상쇄되니 턱보다 낫다.

**측정 설계 — 위상은 스윕이 아니라 샘플링 대상이다.** LLC는 `measure_heights=False`라
지형을 못 본다. 그래서 턱 앞 도착 시의 **보행 위상**이 제어 불가능한 난수이고, 같은
명령·같은 높이여도 결과가 갈린다. 명령을 고정한 채 **턱 시작 x를 1 stride 안에서
균등하게 흔들었다**:

```
stride = vx / step_freq = 1.0 / 3.0 = 0.333 m
x0 ∈ 3.00 + {0, 1/8, …, 7/8} × 0.333      (위상 0~360°를 8분할)
```
기존 `rng_seed` 스윕은 초기 자세 잡음만 흔들어 위상을 덮지 못했다.

★ **위상이 지배 변수임이 확인됐다.** level이 3~5로 흩어졌다(폭 2). 평균 level로 기록했으면
틀렸을 값이고, 기록을 **성공률**로 한 설계가 정당했다.

★★ **`footswing`은 완전히 무력했다.** 0.32로 올려도 위 표 여섯 줄이 **전부 동일**하다.
그런데 개별 위상 결과는 바뀐다:

```
A0        5 5 4 4 4 3 3 4     정렬 -> 3,3,4,4,4,4,5,5
fs=0.32   4 4 3 3 5 5 4 4     정렬 -> 3,3,4,4,4,4,5,5     ← 다중집합이 같다
```

즉 발을 높이 드는 것은 **어느 위상이 성공하는지**를 바꿀 뿐 **얼마나 자주 성공하는지**는
못 바꾼다. 실패 원인이 발 높이 부족이 아니라는 직접 증거다.

> 애초에 "LLC만으로는 턱을 못 넘는다"를 말할 수 없었던 이유: 요철 a=0.06을 5/5
> 통과했고 그 지형의 단차는 평균 0.040 m·최대 0.12 m다 — **보이지 않는 4 cm급 단차를
> 이미 흡수하고 있었다.** 턱은 영구 상승·전폭이라 불리하고 조주 구간이 있어 유리하다.
> 부호를 예측할 수 없으므로 쟀고, 그 결과가 위 표다.

주의 — 옛 프리셋 `(0.03, 0.03, 0.03, 0.04, 0.04, 0.05)`은 **못 쓴다.** 1~3단이 동일 난이도라
사실상 3점만 구분하고, 전 구간이 요철이 이미 통과시킨 0.04 아래다 — 요철 1차 사다리와
같은 천장 치기를 반복한다. 그래서 등간격으로 재설계했다.

### 3.5 외나무다리 — ★ 제외 확정. 재고 있던 것은 다리 폭이 아니라 제어기였다

**① 발 간격** (`scripted.foot_track`, 평지, 시드 3):

| sw 명령 | W_foot | 구간 이득 dW/dcmd | 표류 D |
|---|---|---|---|
| 0.12 | **0.275** | — | 0.179 |
| 0.24 | 0.334 | 0.62 | 0.263 |
| 0.42 | 0.520 | 1.12 | 0.753 |

★ **비대칭 포화다.** 넓히는 쪽은 1:1로 듣는데(이득 1.12) 좁히는 쪽은 1/3만 듣는다(0.37).
중립(0.25, W_foot≈0.34)에서 하한까지 끝까지 좁혀도 **0.065 m(19%)뿐**이다.
→ **발 간격의 바닥은 0.275 m**, 기하 바닥(다리 전폭) = 0.275 + 2×0.023 = **0.321 m**.

★ **표류가 발 간격과 같이 커진다** (0.179 → 0.753). 외나무다리에서 `stance_width`를
넓히는 것은 기하로 얻고 항법으로 잃는 게 아니라 **양쪽 다 손해**다.

**② hold A/B — 경사와 정반대다:**

| | level | 벽 | 다리 밖 착지 |
|---|---|---|---|
| `hold=1` | **5.00** (5/5) | 0.49~0.60 | 0.5% |
| `hold=0` | **2.00** (5/5) | 0.88~1.06 | 0.8% |

진로 유지기 하나가 벽을 **0.88 → 0.55로 40% 밀었다.** 경사에서는 같은 장치가 level을
전혀 바꾸지 못했다.

> **경사는 추진 한계, 외나무다리는 항법 한계다.**

★ 그래서 `modules.beam()`의 "열린 루프로 재라"는 옛 원칙을 철회한 것이 옳았다. 근거였던
"보정을 넣으면 내 보정기 성능을 재게 된다"는 경사 A/B에서 반증됐다. 그대로 뒀으면
**0.88을 "LLC의 한계"로 기록**했을 텐데 실제로는 0.55다 — 60% 과대평가할 뻔했다.

**③ 주의 — 그런데 이 0.55도 확정할 수 없었다. 결함 둘:**

- **`need` 공식이 코스 길이에 의존했다.** `need = 2×(max|y_foot,world| + r)`로 월드
  좌표를 썼는데 거기엔 표류가 섞여 있고, 표류는 거리에 따라 자란다 — 평지 10 m에서
  D=0.179였던 것이 사다리 21 m에서 **0.350**이 됐다. 로봇의 성질이어야 할 수가 코스
  길이에 따라 변하면 설계에 쓸 수 없다.
  → **기하(길이 무관)와 표류(길이 의존)를 합치지 않는다.** `foot_track`은 이제
  `floor = W_foot + 2r`와 `D`를 따로 낸다.
- **다리 *사이*가 전폭 12 m였다** (`_slab`이 `PLATFORM_W=6.0`을 반폭으로 쓴다).
  다리마다 3 m짜리 자유 표류 구간이 있어서 로봇은 거기서 밀린 채 다음 다리에 도착한다.
  즉 사다리가 잰 것은 "얼마나 좁은 다리를 걷나"가 아니라 **"12 m 벌판에서 얼마나
  직진하나"** 였다. 영상에서 "폭은 넉넉한데 직진이 안 돼서 떨어진다"로 보인 것이 이것이다.
  → `BEAM_APPROACH_W = 2.0`(미로 통로 폭)으로 좁히고 `_report_off_beam`이 표류를
  **다리 위에서만** 재도록 고쳤다.

**④ 재측정 (2026-08-09)** — 사다리 `(0.80, 0.64, 0.55, 0.45, 0.39, 0.32)`, 통로 폭 2 m, 시드 5.
`hold=1` → **level 2.40**(0.55에서 실패), `hold=0` → level 1.00.

| | 값 | 실패한 다리(0.55)의 반폭 |
|---|---|---|
| 다리 위 표류 max\|y_body\| | **0.297 m** | 0.275 m ← **넘는다** |
| 딛는 발 max\|y\| | 0.375 m | |
| 다리 밖 착지 | 0.8% | |
| 발 기하 반폭 (W_foot/2 + r) | 0.161 m | 여유 **1.7배** |

★ **몸 중심이 다리 밖으로 나간다. 발은 다리 위에 있었다.** 이 사다리가 재고 있는 것은
다리 폭이 아니라 **진로 유지기의 정상상태 오차**다.

그리고 그 오차는 게인 문제가 아니라 **구조다.** `heading_hold`는 적분항이 없는 순수 P
종속 루프(y → ψ_des → yaw)라 **상수 외란을 제거할 수 없다**(type-0).
LLC의 요속 편향 ω ≈ 0.118 rad/s를 대입하면

```
y_ss = ω / (k_psi · k_y) = 0.118 / (1.5 × 0.5) = 0.157 m
```

관측 0.297의 절반이 이 항이다. 게인을 올리면 줄지만 0이 되지 않는다.

⇒ **`slit`과 같은 부류다**(횡방향 정밀 정렬 요구 > 고유 표류). 미로에 넣지 않는다.
그와 동시에 `slit`의 유보("beam 실측이 끝나면 같은 근거로 판정된다")도 확정됐다.
→ [decisions/0002-beam-slit-제외.md](decisions/0002-beam-slit-제외.md)

### 3.6 측정을 무효로 만들 뻔한 함정들 (재발 방지)

| 함정 | 증상 | 조치 |
|---|---|---|
| 지형이 렌더되지 않음 | 영상에서 "허공을 걷는다" | `TERRAIN_GROUP=5`가 기본 렌더 옵션 밖. `check.render()`가 그룹 (0,1,2,5)를 명시로 켠다 |

| `Limit.usable` | `direction="min"`에서 실측보다 **덜 안전한** 값을 통과시킴 | `value / margin` → `value * margin`으로 통일 |
| 착지 발판 부족 | 2 cm 턱에서 "낙하"로 집계 | `RUN_OUT`을 16 m로. `seconds × vx_max` 이상 |
| `level` 판정 기준 | 램프 **오르는 도중**을 통과로 집계 | 장애물 **끝** + `CLEAR_MARGIN` |

| `height=` kwarg 충돌 | `MjrRect(...,-0.22)` → GL 오류로 오인 | 렌더 인자를 `px_w`/`px_h`로 개명 + 미지 kwarg 가드 |

### 3.7 PPO가 대조군을 못 이겼다 — P2 폐기의 직접 근거

`gap` 사다리 PPO 실측(`runs/p2_gap`, 6.9M 스텝)에서 **8D 명령이 사줄 수 있는 지형 능력이
3 cm**로 나왔다. 대조군인 "고정 vx 최대 명령" 하나와 **동일한 level 1**이었다 —
PPO가 8축을 동시에 굴려도 무식한 직진을 못 이겼다.

주의 — **이 "3 cm"를 지형 일반으로 읽지 말 것.** 그것은 `gap` 하나의 수이고, gap은
**지면이 없는 유일한 지형**이라 가장 불리한 표본이었다. 나중에 실측한 셋은 통과
가능했다(경사 20°, 터널 0.291, 요철 진폭 0.06). "지형 정보가 발 착지 계층에 닿지
않는다"는 진단은 그대로 맞지만, 그 결과가 **모든 지형에서 3 cm**인 것은 아니다.
→ [decisions/0001-지형-돌파-폐기.md](decisions/0001-지형-돌파-폐기.md)

## 4. 처리량

### 4.1 충돌 필터가 지배 요인 (2026-07-29, L4, 512 env, `mjx.step` 1회)

| 설정 | 후보 쌍 | 물리 steps/s | 배속 |
|---|---|---|---|
| `full` (menagerie 원본) | **843** | 22,504 | 1.0× |
| **`world`** (자기충돌 해제) | **42** | **160,611** | **7.1×** |
| `feet` (발·몸통만) | 12 | 184,547 | 8.2× |

원인: menagerie `go1.xml`은 43개 geom을 전부 `contype=1/conaff=1`로 두어 서로가 서로와
충돌한다. 그런데 평지에서 실제 접촉은 **4개**(발 vs 바닥)뿐이고, 발 외 39개는 전부
`condim=1`(무마찰) — **자기충돌 방지 전용**이다.

★ **솔버는 병목이 아니다.** 같은 조건에서 4/8과 8/16의 차이는 **11%뿐**이었다
(21.1 vs 23.5 ms). 솔버 반복을 4배 늘려도 시간이 거의 안 변한다는 것은 `mjx.step` 시간의
대부분이 충돌 검사에 있다는 뜻이다. **느리다고 `iterations`부터 낮추면 정확도만 잃고
속도는 못 얻는다.**

`world`가 `full`과 동등한지 A/B로 확인했다 — vx 0.864 / vy 0.480 / yaw 1.058, `min_z`까지
**완전히 동일**. trot·게걸음·회전에서 자기충돌은 발생하지 않는다.
`feet`는 추종값이 `world`와 미세하게 다른데(0.862 vs 0.864) **그것이 곧 다리 geom이 실제로
지면에 닿는다는 증거**다 — 그래서 안 쓴다.

### 4.2 미로에서 40배 느려졌다 — broadphase (2026-08-10)

| 코스 | 월드 geom | HLC steps/s | 5.9M ETA |
|---|---|---|---|
| 평지 | PLANE 1 | **3,096** | 32분 |
| 미로 | PLANE 1 + BOX 13 | **78** | **21시간** |

**진단 — 세 실험이 각각 하나씩 배제했다.** 이 순서가 요점이다:

| 실험 | 결과 | 배제 |
|---|---|---|
| 벽 직선 병합 33 → 13 geom | 78 | 벽 **개수** 아님 |
| env 2048 → 512 | 78 → 81 | **메모리·GPU 점유** 아님 |
| 로봇 geom 43 → 13 (`collision="feet"`) | 78 → **1,205** | ← 쌍의 개수다 |

★ env를 4배 줄여도 처리량이 같다 = **병렬성이 아니라 스텝당 계산량에 묶여 있다.**
"T4가 약해서"가 여기서 배제된다.

**기준선 — MuJoCo C (1 env, 1 스레드): 14,868 물리 steps/s.**

| | 물리 steps/s | C 대비 |
|---|---|---|
| MuJoCo C (1 env) | 14,868 | 1.0× |
| MJX 미로 `world` (2048 env) | 1,524 | **0.10×** |
| MJX 평지 `world` (2048 env) | 85,073 | 5.7× |

즉 미로에서는 **CPU 코어 하나가 T4 + 2048 env를 10배 이겼다.** 평지에서는 같은 T4가
5.7배 이긴다 — 하드웨어가 아니라 구조 문제라는 뜻이다.

**원인.** 바닥은 PLANE이라 `PLANE-SPHERE`/`PLANE-CAPSULE` 해석해로 끝나는데, 벽은 BOX라
`CAPSULE-BOX`·`BOX-BOX` 볼록 클리핑을 돈다. 그리고 **MJX는 기본적으로 broadphase 컬링을
하지 않는다** — 로봇이 미로 반대편에 있어도 벽 13개 전부와 계산한다.

**해결 — 문서에 있는 기능을 안 켜고 있었다** ([01_llc.md §8.5](01_llc.md)):

| 설정 | HLC steps/s | 5.9M ETA | 물리 충실도 |
|---|---|---|---|
| `world` | 78 | 21시간 | 정확 |
| `world` + **`max_geom_pairs=32`** | **708 (9.1배)** | **141분** | 전 geom 유지, k 근사 |
| `feet` (참고, 미채택) | 1,205 | 82분 | **다리가 벽 통과** |

★ 이때 L0(순수 물리)가 **16,105 물리 steps/s**로 MuJoCo C 1코어를 다시 넘어선다.
★★ **그리고 이쪽은 맵 크기에 O(1)이다.** geom 축소는 상수배지만, k는 벽이 13 → 70개가
되어도 좁은단계가 그대로다. 큰 미로에서 학습할 길이 이걸로 열렸다.

중간안으로 만들었던 `collision="maze"`(바닥/벽 비트마스크 분리)는 78 → 109로 **1.4배뿐**
이라 지웠다 — `_apply_collision_filter`가 이제 그 이름을 받으면 예외로 안내한다.
`feet` 대비 11배 격차의 메커니즘은 `CAPSULE-BOX`로 추정되지만 **확인하지 않았다.**

## 5. P4 미로 학습 (2026-08-10) — 게이트 통과

`runs/p4_maze`, **5,898,240 스텝**, 5×5 seed 0, 2048 env, **234분**.

| | 시작 | 최종 | 게이트 |
|---|---|---|---|
| **도달률** | 0.000 | **0.992** | > 0.70 통과 |
| 남은 거리 | 11.200 | 0.029 | — |
| 낙상 | — | 0.008 | — |
| 에피소드 길이 | 160 스텝 | **91 스텝 (9.1 s)** | — |

★ **PPO가 스크립트 제어기(14.4 s)보다 1.6배 빠르다.** 되먹임을 배운 정책이 고정 게인
비례 제어기를 이기는 것이 정상이고, 실제로 그렇게 됐다. 낙상은 사실상 0 — 지형 실측
6종에서 낙상이 한 건도 없었던 것과 같은 그림이다.

### 5.1 학습 전 게이트 둘 — 이 실행이 한 번에 된 이유

- **게이트 ① broadphase 근사 검증** — `max_geom_pairs = 0 / 32 / 64` A/B.
  5시드 중 4개가 소수점까지 동일. k를 32→64로 올려도 기준에 **가까워지지 않았고**
  (시드 0이 오히려 0.1 s 멀어짐) 차이는 전부 HLC 1스텝 단위였다 → 접촉 손실이 아니라
  **혼돈 발산**이다. 영상에서 벽 관통 없음. **k=32 채택.**
- **게이트 ② env가 풀리는가** — 스크립트 제어기가 **5/5 도달**(14.1~15.7 s).
  흐름장·보상·종료가 전부 맞다는 뜻이다. P1에서 도달 불가능한 코스에 6.5M을 태웠던
  사고가 여기서 반복되지 않았다.

### 5.2 ETA 예측이 1.7배 낙관적이었다

```
eval 간격 소요: [9.5, 9.5, 9.5, 9.5, 9.5, 9.5, 9.5, 9.5, 9.5] 분   ← 완전히 일정
정상상태 414 HLC steps/s   (bench 예측 719, ×0.58)
```

변동이 아니라 **상수 오차**다. `bench.breakdown`은 `jax.vmap(env.step)` 하나만 재고 그
위에 얹히는 것을 세지 않았다:

| | 규모 |
|---|---|
| PPO 갱신 | `num_updates_per_batch 4 × num_minibatches 8` × eval구간당 6갱신 = **192회 그래디언트** |
| brax eval | 24회 × `episode_length` 스텝. **`PPOConfig.num_evals` 주석에 이미 "101분 중 18분"으로 기록돼 있었다** |
| AutoReset·Episode 래퍼 / 관측 정규화 | raw `env.step`에는 없음 |

분해하면 **eval ~18% + 갱신 ~30% = 42%**이고, bench가 달고 있던 "20~40% 더 걸립니다"는
**갱신만 세고 eval을 빼먹은 값**이었다. → 실측 계수 **×0.58**을 넣어 raw와 실제를 두 줄로
내게 고쳤다. 첫 eval 구간만 11.9분(+2.4분)인 것은 **학습 스텝 그래프의 별도 컴파일**이다
— eval 그래프 컴파일(3.9분)과 다른 단계다.

### 5.3 ★ 예산의 절반이 낭비였다

| 스텝 | 경과 | 도달률 |
|---|---|---|
| 983k | 44분 | 0.617 |
| **2.46M** | **101분** | **0.961** |
| 4.42M | 177분 | 0.992 |
| 5.65M | 225분 | 0.992 (진동) |

**최고점의 95%에 2.46M(전체의 43%)에서 닿았고, 나머지 3.4M(140분)이 산 것은 3%p다.**
다음 실행은 `num_timesteps ≈ 3.2M`이면 충분하다. `eval.curve()`가 이 무릎점을 자동으로
찾아 권장값을 낸다.

주의 — 반대로 **`num_evals=25`는 유지할 값이다.** eval이 18%를 먹지만 **9.5분마다 곡선을 본
덕에** 이 수렴 판단이 가능했다. 10으로 줄였으면 못 봤다.

## 6. P5 일반화 판정 — 코드 완료, 실행 대기

★ **미로 하나는 MJX 모델 하나이므로 학습 seed의 99.2%는 레이아웃 암기와 구분되지 않는다.**
관측 37D에 절대좌표도 맵 크기도 없으니 원리적으로는 크기·배치 무관이어야 하지만,
그것은 **가설이지 결과가 아니다.**

`wtw_nav/eval.py`의 `report()`가 학습 미로 + 미학습 배치(seed 7·13) + 큰 미로(n=8·11)를
한 번에 돌려 판정한다. 학습 미로만 높으면 암기다.

```python
from wtw_nav import eval as E
pol, cfg_tr, log, step = E.load("checkpoints/hlc_p4_maze.pkl")
E.curve(log)          # 수렴 지점 → 다음 실행 예산
E.report(pol, n=20)   # 5줄 평가 세트, 실패 원인 분류 + 실패 영상
```

실패 원인은 `reached / fell / stuck / timeout`으로 나눈다 — 고칠 곳이 각각 물리 /
흐름장·라이다 / 예산으로 다르기 때문이다. 주의 — 타임아웃은 brax truncation이라 `done`에
서지 않으므로([02_hlc.md §5.2](02_hlc.md))
세 원인을 `done` 하나로 가를 수 있다.

주의 — **큰 미로에서 떨어지면 먼저 의심할 것은 유도벡터 `d_norm`** 이다 — 관측 중 유일하게
`_course_len`으로 정규화되어 코스 길이에 따라 변화율이 달라진다.

### 7.1 `yaw_bias` 측정 (beam 재개 조건)

`ActionConfig.yaw_bias`는 배선돼 있으나(`command_filter`에서 `vx_bias`와 같은 자리에서
감산, 기본 0.0 = 무효) **측정 함수가 없다.** `beam`을 다시 열려면 이 값을 실측해 넣고
다리 위 표류가 **0.16 m 아래**로 떨어지는 것을 확인해야 한다.

★ 그리고 그때도 고정 게인 스크립트가 아니라 **학습된 HLC로 재는 것이 맞다** — 지금
재면 로봇의 값이 아니라 내 제어기의 값이 된다.

### 7.2 `beam` 판별표 (설계는 끝, 재개 시 재사용)

| 관측 | 결론 |
|---|---|
| 실패 폭 ≈ `W_foot + 2D` | 예측대로 — 둘의 합이 한계 |
| 실패 폭 ≈ `W_foot`, `max\|y\|` 작음 | **발 간격이 한계** (항법 무죄) |
| 실패 폭 ≫ `W_foot`, `max\|y\|` 큼 | **항법이 한계** ← 실제로 이것이었다 |
| 발이 다리 밖을 밟은 스텝 존재 | 착지 위상 문제 |
